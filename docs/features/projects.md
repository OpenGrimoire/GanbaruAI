# Projects

Projects are the structured work layer for calendar scheduling. The user-facing hierarchy is:

1. **Group:** a top-level container for related projects. A company, team, personal routine, or broad life category can be a group.
2. **Project:** the scheduleable unit selected from the calendar event panel. A product under a company and a routine item such as Eat or Exercise are both projects.
3. **Section:** a project-local way to organize tasks. Sections are flexible and user-defined.
4. **Task:** the actionable work item. Tasks can have subtasks, status, priority, labels, dates, estimates, dependencies, and calendar links.

Do not add another user-facing hierarchy level between group and project. The event panel picker exposes only groups and projects so scheduling remains fast.

## Defaults

Fresh databases create one normal group named Routine. Its default projects and visible event color labels are:

- Eat, Color 14
- Learning, Color 9
- Reading, Color 26
- Exercise, Color 1
- Hygiene, Color 16
- Social, Color 22
- Chores, Color 5
- Leisure, Color 32
- Meditate, Color 24
- Sleep, Color 31

Routine is not a special object type. It is a group, and each item under it is a project. Users can create additional groups and projects from the Projects view or from the event panel project selector.

Routine defaults can be hidden or archived like any other project. Hiding keeps the project out of normal navigation and event picking without deleting its history. Archiving retires a project from scheduling while keeping its tasks, events, and future notes recoverable from the Projects view.

Routine default projects use their own project names as default event names. They start with no project-specific default duration. They also start with Default Pomodoro set to None except Learning, which starts with Adaptive. User-created projects start with no default event name. Project idle settings use global Focus defaults unless the user switches a project to custom idle settings.

Each project starts with a General section and default statuses: Backlog, To do, In progress, In review, Blocked, and Done. Default status colors use event palette slots 31, 32, 20, 24, 3, and 14 respectively. Each project also starts with default priorities: Low, Normal, High, and Urgent, with event palette slots 31, 20, 8, and 3 respectively.

## Current implementation

The Projects tab now has an initial project management surface with:

- The Projects frontend is split into a workspace shell, header, toolbar panels, task finder, bulk action controller, first-class List view, list row and column pieces, and focused detail or settings section components. Shared display, scheduling, and list view calculations live under `$lib/projects/` so labels, chips, scheduling windows, list grids, selected-task cleanup, and active filter chips can be tested without Svelte, DOM, or Tauri.
- Group and project navigation lives in an on-demand project selector opened from the project header, not as a persistent left rail. The `Group / Project` breadcrumb uses separate hover and click targets: the group segment opens a compact group panel with an adjacent project sub-panel, while the project segment opens the current group's project panel directly. The selector is fixed to the active breadcrumb segment so toolbar scrolling and content overflow cannot clip it. The selector panels reuse the calendar event project picker behavior, size to their content until they reach the Projects tab bounds, then scroll internally with fade indicators and dedicated scrollbars. The Projects tab selector adds only the hidden and archived recovery toggle.
- Project icons use a shared Notion-like picker in project settings. The picker supports grouped built-in emoji from a generated Unicode emoji catalog, emoji skin tone selection, reusable custom emoji, Lucide icons with optional color selection where the surface enables it, one-off uploaded image icons, recent choices, search, icon-based category rails, random selection, and an explicit remove state. Project settings stores Lucide icons without icon-specific colors so icons inherit the readable foreground color of their current surface. Uploaded icons accept PNG, JPEG, and WebP files up to 3 MB. SVG files are blocked for security because they can contain interactive or external content. Project creation templates still use their compact built-in starting icons in this pass.
- Project group reassignment from project settings.
- Project creation from the navigator and event panel picker supports compact templates: Blank, Software, Course, Routine, Reading, and Chores. Templates choose the starting icon, scheduling defaults, and initial sections, while preserving the same Group -> Project -> Section -> Task model.
- Project lifecycle controls for Active, Hidden, and Archived. The navigator hides inactive projects by default and has a compact recovery toggle for hidden and archived projects.
- The active project and active Projects view persist in the active Ganbaru AI folder config, so returning to Projects after restart reopens the same working surface when the project still exists.
- The Projects store loads group and project metadata globally, then loads task-heavy rows for opened projects and merges them into a small in-memory cache. This keeps navigation complete without forcing every task in the database into the first Projects snapshot.
- Project switching keeps the current workspace visible until the target project data is loaded. Cached projects switch immediately, while first-time project loads avoid briefly rendering empty sections or half-loaded controls.
- The project header uses the same visual shell as Calendar: a single toolbar row using the calendar header background, row height, and bottom divider. Project identity appears as a single-line `Group / Project` breadcrumb that doubles as the project selector trigger, while the view tabs sit in the right-side toolbar cluster immediately before Filters, Sort, Columns, Group, and Project settings. Those toolbar controls open viewport-aware anchored panels instead of pushing extra bars into the workspace. Task search opens as a bottom-centered finder with `Ctrl+F` or from the overflow menu, and task creation stays close to the relevant section instead of living in the header.
- The Projects content area uses the same internal calendar surface background as Calendar, so project planning and calendar scheduling feel like related work surfaces instead of separate apps.
- List row grouping uses a dedicated compact Group panel. Task filters, sorting, visible columns, saved task views, archived-task visibility, and hidden-section visibility use progressive disclosure through compact anchored Filters and Columns panels. The first panel is a Notion-like row menu with an icon, field name, current value, and chevron for each setting. Choosing a row opens a second adjacent panel with the actual selectable options.
- List rows use a table-like grouped surface with stable column headers, thin dividers, dedicated custom scroll gutters, and column toggles for status, start date, due date, priority, assignee, reviewer, estimate, scheduled blocks, dependency links, and selected custom fields. List columns default to compact content-sized tracks instead of stretching to fill the viewport, with a wider automatic default for the Name column; users can resize visible columns from the right edge of each header, and those widths are stored per project. Double-clicking a resize edge resets the column to its default width when the default fits the content, or expands it to the content-fit width when the default would truncate values. The final header track shows an inert add-column affordance for the future column creation flow. Long values truncate inside their cells, while horizontal dividers still span the full list frame. Assignee and reviewer are local placeholder ownership columns until the multi-person model is designed; both default to the current user and render as compact initials avatars. Group names and the Name column start on the same grid line. Section and group headers plus the Add section row stay horizontally anchored while column headers and task rows scroll sideways; horizontal dividers remain anchored to the list frame. The leading cells are reserved for hover-revealed selection squares and row chevrons, so selection does not push task titles out of alignment. Group headers stay quiet and do not show task counts. Column choices are stored per project and restored with saved task views.
- Saved task views for each project. A saved view captures the active project tab, search, filters including task labels and custom fields, sort including custom-field sort, visible List columns including custom-field columns, active List row grouping, collapsed section state, and archived-task visibility, then appears as a reusable chip in the Projects header.
- Task archive and restore. Archived tasks are hidden by default, recoverable through the task filter bar, and kept as structured history instead of being hard deleted.
- Task multi-select in List and Kanban views, with bulk done, reopen, priority, archive, and restore actions.
- Project views for Dashboard, List, Kanban, Calendar, and Gantt. List remains the default view. While the Projects tab is active, `1` through `5` switch those project views in visible order unless focus is inside an editor, dialog, picker, task finder, or toolbar panel.
- List rows can be organized by section, status, priority, due-date bucket, or scheduled state. Section grouping keeps section editing, ordering, hiding, archiving, and section-scoped quick add. Section creation uses the same quiet inline add-row pattern as section-scoped task creation. Other row groupings are read-only projections over the same tasks, keep their empty buckets visible, and expose quick-add rows when the group can be represented by task fields. Scheduled task creation stays tied to calendar block scheduling, so the Scheduled bucket itself does not create a task without a schedule.
- Gantt renders a real proportional timeline for dated tasks and milestones, grouped by sections, with today, overdue, blocked, done, dependency line indicators, and finish-to-start dependency conflict flags. Task bars can be dragged to move the date range, resized from visible start and end handles, and milestones can be dragged to a new date. When conflicts exist, Gantt can propose dependency date shifts, show each affected task and reason, and apply the shifts only after explicit user action.
- Dashboard reports task counts, completion, open estimates, scheduled hours from loaded project calendar events, blocked tasks, upcoming deadlines, overdue tasks, unscheduled due tasks, tasks missing estimates, recent task changes, and recently completed tasks.
- A compact project settings panel for editing project name, icon, event defaults, Default Pomodoro, project idle defaults, default focus playlist, and default break playlist. Event defaults include the event color, default event name, default event duration, and the music playlist selectors. The playlist selectors currently expose only None until playlist management provides real choices. Empty default event name stores None. The default duration uses a preset selector with None, common timed durations, All day, and a custom minutes or hours entry capped at 24 hours with up to two decimals. None stores no project-specific duration. Selecting a project in an existing event draft keeps the current event length, while project-originated scheduling with no existing duration uses the app default. Default Pomodoro is explicit: None creates project events without Pomodoro, presets show their compact `F / SB / LB / C` rhythm summary, and Custom stores the same simple count rhythm fields used by the event panel. New projects default to no event name, the Adaptive Pomodoro preset, global Focus idle settings, and no playlist defaults. Turning off global idle settings exposes project-specific idle pause by default and idle threshold controls using the same 1, 2, 3, 4, 5, 10, and 15 minute options as Focus settings. It opens from the settings toolbar button as the same anchored panel family used by filters and columns, with the same clean row language used by app Settings: bold group headings, plain labels, right-aligned custom controls, custom popover selectors, divider-separated groups, and the calendar-style custom scrollbar.
- Project task status editing inside project settings. Statuses are project-local and support editable names, event-palette colors, category selection, drag-handle column reordering, and confirmed deletion when no tasks use the status: Not started, Active, Blocked, or Done. Status values render as compact soft-color pill tags with a small color dot and contrast-aware text.
- Project task priority editing inside project settings. Priorities are project-local and support editable names, event-palette colors, drag-handle reordering, and confirmed deletion when no tasks use the priority. Priority values render as plain text with a filled flag icon using the priority color, rather than label-like pills.
- Project label management inside project settings. Labels are project-local and support creation, renaming, event-palette colors, reordering, and confirmed deletion. Deleting a label removes it from tasks while preserving the tasks and task history.
- Project custom field management inside project settings. Custom fields are project-local and support Text, Number, Date, Select, Multi-select, Checkbox, and URL field types. Select and Multi-select fields manage their own ordered option lists.
- Section creation, collapse, renaming, reordering, hiding, archiving, restoring, and section-scoped task creation. Section rename drafts show a compact inline confirm button only when the name has an unsaved valid edit. Section hide, archive, and restore actions live in a contextual options menu that appears next to the section name on hover or focus.
- Manual task reordering inside List sections and Kanban status columns. List section groups and task rows are dragged by pressing the group header or row area and moving the pointer past the drag threshold. The List view does not reserve a dedicated drag icon column for groups or tasks. Interactive controls such as status, priority, selection, and section collapse do not start drags. List sections and task rows do not duplicate drag behavior with separate up/down controls.
- Task status, priority, start-date, and due-date changes happen through List column pickers. Choosing a terminal status completes the task, choosing a non-terminal status reopens it, and the start date and due date columns use the shared mini date picker. When both dates are present, the picker highlights the full range. Today stays bold when it is not an endpoint, and past days keep a muted foreground even when they are part of the selected range. Selecting a start date after the current due date moves the due date to the same day, and selecting a due date before the current start date moves the start date to the same day. If both date columns are visible and the user sets only one endpoint, the List view opens the missing endpoint picker next; the user can ignore it by clicking elsewhere. Dated list cells can also store an optional start or due hour through the same 30-minute time picker used by the calendar event panel. Removing the hour keeps the date intact, while clearing a whole date is handled outside this picker until the dedicated clear-date flow is redesigned.
- Kanban cards can move to adjacent statuses without opening the task detail panel. They also support drag and drop through a visible card handle; dropping onto another card preserves manual Kanban order with lightweight midpoint sort values.
- Task filters cover status, section, priority, due-date state, custom due-date ranges, scheduled state, dependency-link state, task labels, and project-local custom fields. The blocked filter includes blocked statuses, blocker reasons, and dependency-blocked tasks. Sort options cover manual order, status, section, priority, due date, next loaded scheduled block, created date, updated date, estimate, and project-local custom fields.
- A task detail panel for editing title, description, status, section, priority, task type, estimate, dates, blocker reason, and milestone state.
- Project-local task labels can be created from task details, reused across tasks in the same project, removed from a task, managed from project settings, used as task filters, persisted in saved views, and shown as compact color-marked chips in List rows. Scheduled task chips show the next loaded scheduled block when one is available, otherwise they fall back to the linked scheduled-block count.
- Project-local custom field values can be edited from task details. Values are typed in SQLite rather than stored as opaque JSON, meaningful value changes are recorded in task history, selected custom fields can appear as compact List row chips, and custom fields can be used as task filters and sort modes.
- Dependency editing inside task details. Tasks can show and edit `Blocked by` and `Blocks` relationships, with same-project validation and cycle prevention in the backend.
- Lightweight checklist items inside task details, with add, rename, reorder, complete, and delete actions.
- Real subtasks, stored as tasks with `parent_task_id`, visible under parent tasks and in the task detail panel. Subtasks can be reordered under their parent, promoted back to top-level tasks, and top-level tasks without subtasks can be demoted under another top-level task. They are heavier than checklist items because they have their own status, priority, dates, scheduling, and detail panel.
- Task change history is recorded in SQLite for creation, scheduling, event unlinking, dependency changes, status changes, completion, reopening, archive actions, and meaningful field edits. Task detail saves can include an optional change reason, and the reason is shown with the affected history entries. Task details show the recent history for the selected task, while Dashboard shows recent changes across the selected project.
- Bulk quick scheduling from selected tasks. The selected active tasks can be scheduled as sequential calendar blocks starting at one chosen date and time, with one task-event link per generated block.
- Existing loaded project calendar events can be linked to or unlinked from a task inside task details.
- Task details search project calendar events directly from SQLite when linking existing scheduled blocks, with optional date-range filters. Already linked blocks for the selected task remain visible even when they are outside the currently loaded calendar window.
- A project-filtered calendar surface using the same `CalendarView` engine as the global calendar. It reuses calendar window loading, recurrence rendering, event panels, drag and resize behavior, delete/archive handling, view switching, and Pomodoro rail rendering. The surface shows events linked by `project_id`; when task filters are active, it narrows to events linked to matching tasks. Pure sort changes do not hide events. Creating an event from this surface preselects the current project and applies that project's event defaults.

The task detail modal behaves like a focused editing surface rather than an extra hierarchy level. It opens from task rows and Kanban cards, keeps a draft while editing, and adapts to a centered modal, sheet, or fullscreen layout depending on available viewport space. Its title is edited directly in the header, task information is grouped into calm settings-like sections, date fields use the shared mini date picker, and the content area uses the same custom scrollbar treatment as Settings. Its backdrop dims the workspace without blur or heavy contour shadows, and closing with unsaved edits uses the shared discard confirmation.

The project settings panel behaves like a focused toolbar popover with save and discard actions, and it writes defaults plus task status and priority settings directly to the project. It uses compact Settings-style rows and divider-separated groups for identity, event defaults, labels, custom fields, task status editing, and task priority editing, with native select controls avoided in favor of the shared custom popover selector. The panel keeps labels plain, section headings bold, and controls aligned to the right so the limited width remains scannable as the project model grows. Default event duration can be empty, a timed duration, or all day. Those defaults are used when scheduling tasks from Projects and when creating calendar events that select the project. Done-category statuses are terminal, and terminal statuses must use the Done category.

Use checklist items for simple steps that only need done or not done. Use subtasks when the work needs separate ownership later, status, dates, scheduling, dependencies, or notes. Both belong to the task detail panel; neither appears in the calendar event project picker.

Archive tasks instead of deleting them when they may have useful history, linked scheduled blocks, dependencies, subtasks, or future notes. Archiving a parent task archives its descendants so active subtasks do not become hidden under an inactive parent. Restoring a parent restores its descendants for the same reason.

The calendar event panel includes a compact project selector. It shows groups and active projects only; hidden and archived projects are recoverable from the Projects view, not from event creation. Selecting a project saves `project_id` on the event. If the event title is empty and the project has a default event name, that name becomes the event title. Existing event title text is never replaced by project selection. The event color updates to the selected project's event color. Timed events apply the project's default timed duration, Default Pomodoro mode, idle default, and focus playlist when present. A project default event duration of All day switches a non-active timed draft to an all-day event instead. Default duration is not applied to active event edits, so switching projects cannot accidentally resize an event that is currently in progress. A project Default Pomodoro value of None turns Pomodoro off for that event, a preset copies that preset, and Custom copies the stored count rhythm. Project idle defaults either copy the current global Focus idle settings or the project's custom idle pause and threshold. Single-event panels can link active top-level tasks from the selected project without exposing sections or task trees in the project picker. Break playlist defaults stay on the project until the Music runtime surface can consume them.

Task scheduling from Projects uses the task title as the event title, the task's project as `project_id`, the project's event color, default event duration, Default Pomodoro mode, idle default, and focus playlist when present. If the project default event duration is All day, scheduling creates all-day task events instead of timed events. Empty project calendar slots use the project's default event name when present. The task and event are then connected through `project_task_event_links`. Bulk quick scheduling creates separate blocks for selected active tasks so each task stays independently linked and visible in task details. Existing project calendar events can also be searched and linked from task details. Links are valid only when the task and calendar event belong to the same project.

## Data ownership

Projects, groups, sections, statuses, priorities, tasks, task dates and optional task hours, task labels, custom fields, custom field options, custom field values, task history, task dependencies, project view preferences, reusable custom emoji metadata, and event links are structured data. SQLite is the source of truth for this layer.

Project and group icon values are stored in the existing `projects.icon` and `project_groups.icon` columns. Legacy icon slugs such as `folder` remain valid and are treated as Lucide icons. New values use explicit prefixes for no icon, built-in emoji, Lucide icons with color, reusable custom emoji, and one-off asset icons. Custom emoji image bytes and one-off image icons are copied into `assets/project-icons/` under a content hash; remote image URLs are downloaded once rather than hotlinked. Asset icon values only accept PNG, JPEG, and WebP paths. Unsupported asset references, including manually inserted SVG or GIF paths, fall back to the default folder icon instead of rendering.

Transient UI preferences such as the active project and active Projects view live in the active Ganbaru AI folder `config.json`. They are folder-specific, recover from invalid stored values, and do not become part of task or project history.

Notes remain separate. Future project notes should be markdown documents under the Ganbaru AI folder and indexed by SQLite, but notes are not part of this slice.
