# Notes

The Notes system combines a local SQLite page and block editor with file-backed Markdown working documents from the selected project's working folders. SQLite remains canonical for Notes pages and blocks. Markdown import and export for that model remain derivative. Working-folder `.md` files are a separate file-authoritative model and are never imported automatically.

The model follows public Notion API concepts where they are useful locally: pages, parents, blocks, rich text arrays, child pagination, timestamps, trash state, and archive state. It does not depend on Notion services, private internals, or hosted infrastructure.

## Source of truth

The project Notes tree mixes SQLite folders, SQLite pages, working-folder roots, filesystem directories, and Markdown files with stable source-aware node identities. A working-folder root appears only when it contains a supported `.md` descendant. Scanning recursively prunes empty branches and excludes symbolic links, `.git`, dependencies, build output, caches, non-UTF-8 paths, unsafe entries, and files beyond the supported size. Depth, entry count, and path length are bounded, and a truncated result is identified explicitly. Title filtering includes file and directory names and reveals matching ancestors.

Opening a filesystem Markdown file replaces the editor pane with a dedicated raw editor and sanitized rendered preview. It provides explicit Save, dirty state, guarded navigation, Refresh, Open externally, and Copy relative path. Reads return a content revision digest. Saves require the expected digest and use atomic replacement. If another tool or AI changes the file while local edits are dirty, Notes refuses to overwrite it and offers Reload, Copy local text, or Open externally. This slice does not create, rename, move, or delete filesystem Markdown files.

Notes are stored in `ganbaru-ai.sqlite`:

- `notes_pages` stores page metadata, parent identity, title cache, properties, project ownership metadata, icon, cover, trash state, trash entry time, archive state, optional external source identity, and timestamps.
- `notes_folders` stores project-scoped navigation folders with optional folder parents. A nullable `notes_pages.folder_id` places workspace-parented pages in those folders without changing the Notion-shaped page parent.
- `notes_page_aliases` stores alternate local names for active pages and database row pages. Aliases are canonical SQLite metadata, participate in search, and resolve local Notes links that were written with a stable alias, title, or target parameter instead of a page id.
- `notes_blocks` stores the canonical block tree. Each row has a page id, parent identity, block type, type payload, rich text, plain text cache, child state, trash state, sort order, optional external source identity, and timestamps.
- `notes_databases` stores local child database metadata, parent identity, title rich text, optional icon and cover, timestamps, and optional external source provenance. `notes_data_sources` stores the initial data source for each source database, including title rich text and validated property schema JSON. Linked database blocks create another database shell and view row without duplicating the data source. `notes_database_views` stores local database views, starting with the first table view for the initial data source, and carries table property order, hidden properties, column widths, board grouping and card properties, gallery card settings, list grouping and row properties, calendar date property and range settings, timeline date property, grouping, and range settings, filters, sorts, and row open mode. `notes_data_source_relation_links` stores normalized database relation link rows derived from row page properties for backlinks, search, and target validation. `notes_data_source_rollup_cache` stores rebuildable computed rollup page property values and is invalidated when related source or target data changes. Formula properties store only their local expression in the data source schema and are evaluated from current row properties when rows load.
- `notes_page_templates` stores reusable page template metadata, page properties, icon, cover, source page identity, and timestamps. `notes_page_template_blocks` stores the canonical template block tree. Templates are SQLite data, not markdown or rendered HTML.
- `notes_page_history_settings` stores the shared Notes history retention window. The supported values are off, 7, 30, 90, 180, and 365 days, with 30 days as the default. Off is stored as zero, prunes retained history in the affected scope after confirmation, and prevents new page snapshots or project checkpoints. `notes_page_history_snapshots` is the active fine-grained single-page recovery format. Project versions use content-addressed bundles and manifests so unchanged rows are shared across checkpoints.
- `notes_history_bundles` stores immutable canonical JSON rows and project manifests by SHA-256 hash. Payloads use raw storage or zlib only when compression is smaller. Large payloads use bounded chunks described by `notes_history_bundle_chunks`. `notes_project_history_versions` stores project checkpoints, `notes_project_history_bundle_references` keeps their bundles live, `notes_project_history_asset_pins` keeps referenced managed files live, and `notes_project_history_dirty` persists checkpoint scheduling across app restarts.
- `notes_comment_threads`, `notes_comments`, and `notes_comment_thread_anchors` store page discussions, block comments, inline text-range anchors, status, author metadata, and soft-delete state. `notes_comment_thread_reads` stores per-local-user read timestamps for unread counts. Read state is local collaboration metadata, not markdown content.
- `notes_suggestions` stores local suggested edits for text block ranges, including original text, proposed replacement text, author snapshot, timestamps, range offsets, context anchors, and accepted or rejected state. Suggestions are collaboration metadata, not markdown content.
- `notes_collaboration_operations` stores a local operation log for comment and suggestion mutations so future self-hosted sync has stable operation shapes, actor snapshots, entity versions, and explicit conflict policies. It is not a hosted sync queue and does not make read state syncable.
- `notes_mention_notifications` stores pending, delivered, and dismissed local notification rows derived from reminder mentions, user mentions, and project task mentions in canonical rich text. Delivery is performed by the local app process and never by hosted infrastructure.
- `notes_assets` stores normalized metadata for managed Notes files copied under the Ganbaru AI assets folder, including local page icons, page covers, block attachments, property files, comment attachments, and import sources. It validates managed relative paths, MIME type category, positive byte size, lowercase SHA-256 digest, source type, and available or missing storage state.
- `notes_asset_references` stores the ownership graph from managed files to pages, blocks, data source properties, comments, and import records. Page icon, page cover, media or file block, data source files property, comment attachment writes, and import writes create or clear references instead of embedding raw paths in payload JSON.
- `notes_search_index`, `notes_search_fts`, and `notes_search_index_state` store the rebuildable Notes search projection. They are caches derived from canonical pages, page aliases, row property values, data source schemas, cached rollups, formula outputs, blocks, comments, relations, and managed file references, not a second source of note content.
- `notes_backlink_index` and `notes_backlink_index_state` store the rebuildable Notes backlink projection. They are caches derived from child-page blocks, rich text page mentions, local Notes links, comments, database relations, supported local object mentions, and page alias resolution, not a second source of link truth.
- `notes_unresolved_link_index` and `notes_unresolved_link_index_state` store the rebuildable projection of local Notes links that cannot resolve to an active page or active database row page. They are derived from block and comment rich text, and resolving an entry rewrites the source link to the chosen stable page id.
- `notes_link_facts` and `notes_link_facts_state` store the rebuildable graph projection for pages, database row pages, blocks, properties, comments, managed files, local app objects, and external URLs. They are derived from canonical page metadata, block payloads, row properties, comments, relation rows, asset references, and alias-aware local link resolution.
- Import file candidates from Notion export folders, HTML imports, and Markdown imports must pass through the shared preparation command before any importer writes blocks or properties. The user must explicitly choose to copy a local file from the selected import folder, keep an HTTPS external reference, or skip the reference. Copying validates size, MIME or extension compatibility, and the canonicalized import-root boundary before storing the file as a managed asset with source type `imported`.
- `notes_page_icon_assets` and `notes_page_cover_assets` keep command-specific metadata for local page icon and cover image picking. The shared `notes_assets` row is the cross-feature file registry, and page rows still keep only the validated Notion-shaped icon or cover JSON payload.
- `notes_undo_state` stores a bounded page-local undo and redo stack for editor recovery. It is local operation state derived from canonical rows, not a second source of note content.

Markdown and HTML exports can be regenerated from SQLite. Markdown and HTML imports must be parsed into page and block rows before editing. If an exported file changes outside the app, the app treats that as import input, not as authoritative state.

## Markdown import

Markdown import creates a new canonical Notes page and normal `notes_blocks` rows in one SQLite transaction. It supports the practical first slice for headings, paragraphs, inline HTTP, HTTPS, and mail links, flat lists, to-dos, quotes, dividers, fenced code, external HTTPS images, and simple pipe tables. Safe frontmatter can provide the imported title, while unknown frontmatter fields, unsafe file references, inline images that cannot become media blocks, HTML, reference definitions, and deeper heading levels return diagnostics instead of silently disappearing.

Imported markdown records source provenance as `markdown`, but the markdown text is not stored as an editable authority. Local file references are skipped until the shared import-file policy copies or deliberately references them. Unsupported syntax becomes visible preservation blocks where practical so users can review and convert it after import.

## HTML import

HTML import creates a new canonical Notes page and block tree from sanitized HTML. Notes settings exposes an Import action that accepts pasted HTML or an HTML file loaded into the import preview field, an optional page title, an optional source name, a required project destination, and an explicit choice for keeping HTTPS media references. The importer strips unsafe markup and event attributes before conversion, extracts `<title>` or the first heading for the page title when no title is provided, and records page and block provenance as `html`.

The supported first slice converts headings, paragraphs, inline bold, italic, underline, strikethrough, inline code, HTTP, HTTPS, and mail links, flat ordered and unordered lists, checkbox list items, quotes, fenced-looking preformatted code, dividers, callouts from `aside`, toggles from `details`, simple tables, and image, video, or audio blocks when the user chooses to keep supported HTTPS media URLs. Local, relative, non-HTTPS, or unsupported media references are skipped and reported so they can later pass through the shared import-file policy instead of becoming raw paths. Unsupported elements become visible preservation blocks where practical, while scripts, styles, SVG, math, iframes, unsafe URL schemes, and event attributes return diagnostics and are not stored as editable content.

## Notion API import

Notion API import creates canonical local Notes data from a user-provided Notion integration token and source object ids. Notes settings exposes an Import action for page ids and data source ids, a required project destination, optional workspace source identity, page size, comments, users, and external file reference handling. The token is used only for the request in progress and is not persisted in SQLite, config files, comments, diagnostics, or page payloads.

The importer targets public Notion API version `2026-03-11`. It retrieves pages, recursively paginated block children, data source schemas, queried data source rows, unresolved comments, and optional users. It records request, retry, and rate-limit counts so the user can tell whether the import was delayed or degraded by the remote API. Pages, blocks, wrapper database pages, data sources, database row pages, comment threads, and comments receive `notion` source provenance where the local schema supports it.

Every Notion response is streamed into a byte cap before JSON parsing. Successful responses are limited to 8 MiB, error responses to 64 KiB, and both must declare a JSON media type. Each paginated endpoint is limited to 100 response pages and 10,000 objects, with a 2 KiB cursor cap and repeated-cursor detection. Block-child requests receive only the capacity remaining under the existing 5,000-block limit for the page or row, so recursion and pagination stop at that boundary instead of fetching an oversized remainder. A single retry delay is capped at 10 seconds, cumulative retry waits are capped at 20 seconds, and the existing three-retry limit remains in force. Dropping an in-progress request cancels its response stream.

Remote response bodies are never copied into errors or diagnostics. Authentication, permission, missing-object, conflict, rate-limit, and server failures use fixed local messages plus the HTTP status and source object id already associated with the import action. The integration token and imported page, property, block, and comment content remain absent from diagnostic text.

Supported blocks and properties are converted into the same Notion-shaped local payloads used by the editor. Unsupported blocks become visible unsupported block placeholders with raw source metadata and warnings, while unsupported data source properties are downgraded to rich text properties with diagnostics. Notion-hosted file URLs, file upload ids, and external file references are not fetched automatically. When the user keeps external references, supported file objects are stored as explicit source references; otherwise they are skipped with diagnostics so local Notes data does not silently depend on temporary remote URLs.

## Notion export folder import

Notion export folder import creates canonical local Notes data from an already downloaded Notion export directory. Notes settings exposes a folder import action with a required project destination and toggles for Markdown, HTML, CSV, local file copying, and keeping supported external file references. The importer reads the selected folder recursively within a bounded depth and file count, skips hidden entries and Notion workspace `index.html` sitemap files, and never treats the export folder as an editable source of truth after import.

Markdown and HTML export pages are parsed through the same canonical import paths as standalone Markdown and HTML imports. Local links that point to other files in the export are rewritten into local Notes links by title where a target can be identified. Local media and file references are copied into managed Notes assets only when the user enables copying and the shared import-file boundary accepts the path, size, and target media type. Otherwise the reference is skipped with diagnostics instead of storing raw filesystem paths.

CSV files are reconstructed as local data sources. The first column becomes the title property, remaining columns become rich text properties, and non-empty rows become normal database row pages with `notion_export` source provenance. Markdown or HTML files in the same folder whose stripped title matches a CSV row title become that row page's body content instead of importing a duplicate standalone page. Imported standalone pages, database wrapper pages, row pages, blocks, data sources, and database views record `notion_export` source provenance where the schema supports it.

## Markdown export

Markdown export reads canonical `notes_pages`, `notes_blocks`, and optionally `notes_comments` to produce deterministic derivative markdown. The export includes the page title by default, walks active blocks in stored order, renders rich text annotations, safe links, mentions, inline and block equations, headings, paragraphs, lists, to-dos, toggles, callouts, quotes, code, dividers, simple tables, and media references. Comments are included only when requested, append as a comments section, and omit local read state.

Markdown cannot represent every local or Notion-shaped block losslessly. Unsupported blocks, child pages, child databases, generated navigation blocks, layout containers, local asset references, file upload references, colors, and other approximations return diagnostics instead of pretending the export is complete. The output is a view over SQLite and can be regenerated at any time.

## HTML export

HTML export reads canonical pages, blocks, comments, managed asset metadata, and supported database view metadata to produce a readable derivative zip archive. The selected note action menu exposes an export action for the open page. The dialog can include subpages, managed local assets, database view manifests, comments, and resolved comments. The backend returns the same deterministic archive model that the native save command writes: page HTML files, a CSS file, database JSON manifests where a local database block has view metadata, `manifest.json`, asset metadata, object counts, and diagnostics.

Page content exports as static HTML. Child pages link to their exported page files when they are included in the page tree. Rich text links keep safe HTTP, HTTPS, and mail links, and local Notes links point to exported pages when their targets are in the archive. Managed asset files are copied into the zip only when requested and available in the Ganbaru AI assets folder. Missing, excluded, unsafe, unsupported, or out-of-archive references produce warnings instead of silent loss. Database views currently export as JSON manifests with view settings and row property snapshots rather than a fully interactive database UI.

## JSON graph export

JSON graph export writes a local diagnostic and backup snapshot of the canonical Notes SQLite graph. Notes settings exposes a workspace-level Export action. The dialog can include or exclude rebuildable indexes, page history, templates, and local UI state, and it can write pretty JSON for inspection. The backend returns the export schema version, current applied SQLite migration version, object counts, table counts, warnings, and the exact JSON file content that the native save command writes.

The export groups canonical `notes_*` rows into pages, blocks, comments, data sources, files, templates, history, local state, indexes, and a fallback misc section for future Notes tables. JSON columns such as block payloads, page properties, data source schemas, comments, history snapshots, and template blocks are exported as JSON values instead of stringified blobs. Rebuildable SQLite FTS virtual tables and shadow tables are omitted because `notes_search_index` is included and can rebuild them. Managed asset metadata and references are exported, but binary file bytes stay in the Ganbaru AI assets folder and produce a warning when assets exist.

## Agent bridge export

Agent bridge export writes deterministic derivative markdown for local agents and collaborators that need readable project context rather than a full backup graph. The selected note action menu exposes the export from the open page. The dialog can include subpages, backlinks, database views, project task context, comments, and resolved comments. It can also add one explicit project to the export while the backend still infers linked projects from page and project task mentions in `notes_link_facts`.

The markdown starts with a visible warning that SQLite remains the source of truth. It includes export metadata, selected Notes page content, child database views rendered as markdown tables from the current local view, active project tasks with sections, statuses, priority, schedules, checklist items, and tags, plus backlinks for the exported pages. It does not include a generated timestamp, does not persist export rows, and does not embed managed asset bytes. Missing pages, projects, unsupported markdown shapes, and database export approximations return diagnostics instead of silently pretending the view is complete.

## Round-trip diagnostics

Import and export surfaces show a shared round-trip diagnostics panel after each completed operation. The panel summarizes object counts, warning counts, and diagnostic categories for preserved, approximated, skipped, unsupported, warning, info, and error outcomes. It keeps the older command summaries visible, but adds a consistent breakdown so users can tell whether a file is a complete projection, a readable approximation, or missing some data.

Diagnostics stay tied to the source that produced them where practical. Markdown and HTML import diagnostics can point to source lines, Notion API diagnostics show source object ids, Notion export folder diagnostics show source paths, CSV import diagnostics show source rows, CSV export diagnostics show affected properties, JSON graph diagnostics show table and row ids, and export diagnostics link to local Notes pages or blocks when the backend returns navigable ids. These links are convenience navigation only. They do not turn derivative files, source folders, CSV files, JSON exports, HTML archives, markdown exports, or agent bridge output into authoritative note storage.

## CSV database import

CSV import is a derivative import path for local databases. It never makes the CSV file authoritative. The importer reads a CSV file or pasted CSV text from the table view, maps columns to the current data source schema by property name, property id, or property key, validates cell values, and creates normal database row pages in SQLite only for rows that pass validation.

The preview action is a dry run and writes nothing. It returns mapped columns, skipped columns, valid row counts, skipped row counts, and row-level diagnostics so the user can correct the CSV before importing. The import action creates canonical `notes_pages` rows with `parent_type = 'data_source_id'`, normal first paragraph blocks, Notion-shaped page properties, and CSV source provenance. Invalid rows are left out and reported instead of partially importing broken property data.

The first slice supports title, rich text, number, checkbox, select, status, multi-select, date, URL, email, phone, place, and relation properties. Select, status, and multi-select values must match existing options, and relation values must refer to row page ids in the configured target data source. Files, people, created time, created by, last edited time, last edited by, unique ID, rollup, formula, and button properties are skipped with diagnostics because their values are generated, read-only, computed, or need a dedicated local asset or automation flow.

## CSV database export

CSV export is a derivative view over local database rows. The table view exposes an export action with two modes: current view and full data. Current view exports the table's visible properties, active filters, and active sorts. Full data exports all active row pages and all current data source properties without applying table filters or hidden-property settings.

Headers are deterministic and use property names, with property ids added when names collide. Cells are rendered as CSV-safe plain text from the hydrated row properties in SQLite, including relation titles, computed rollup values, and formula output where available. Structured properties that cannot round-trip through CSV, such as files, people, relations, rollups, formulas, and database buttons, return warnings so the user knows the export is readable but not a complete backup of those property payloads.

## Page model

A page has an object type, id, created and edited timestamps, parent, trash state, archive state, properties, icon, and cover. The first local page slice uses a title property named `title`, shaped as a Notion title rich text array, and also keeps a normalized title cache for fast navigation reads. Newly created local pages start with an empty stored title; the editor and navigation surfaces show the localized untitled label only as placeholder or fallback display text until the user writes a real title. Page icons use the public Notion icon object shape, with editable emoji icons, native icon names and colors, reusable custom emoji, external HTTPS image icons, managed local image file icons, and null removal from the note title hover controls. When present, the icon renders above the title rather than inline beside it. Missing local icon files fall back to the page icon placeholder and mark the managed asset row missing until the file reads successfully again. Page covers use the public Notion file object shape, with editable external HTTPS image covers, imported Notion-hosted file objects, imported file upload references, managed local image file covers, generated local cover images, and null removal from the title hover controls. Missing local cover files show the unavailable cover placeholder and mark the managed asset row missing until the file reads successfully again.

Parents are explicit objects:

- `workspace` for top-level pages.
- `page_id` for subpages.
- `block_id` for pages nested under blocks.

Workspace pages appear at the top level of the project-scoped Notes explorer and compact note navigator. Page-parented child pages appear under their parent page in the page tree, with local expanded state that does not change the canonical page graph. Navigation loads page metadata lazily: roots are loaded first, expanded page ids load their direct child page metadata, and selected pages load their ancestor path so navigation remains understandable without loading page block bodies. Breadcrumbs resolve the selected page's parent chain from SQLite even when ancestors are not loaded in the navigation tree. Active ancestors are navigable, while archived, trashed, or missing ancestors stay visible with status text instead of pretending to be normal pages. Block-parented child pages remain addressable through breadcrumbs and visible child-page blocks until navigation can resolve loaded block ancestry across the whole workspace.

### Folder model

Folders are first-class local navigation containers modeled after a filesystem hierarchy. They are not empty pages, cannot contain blocks, and are not added to the public Notion parent union. A folder belongs to one project and can contain nested folders plus workspace-parented pages from that same project. A page inside a folder can still own normal page-parented subpages, so imported Notion hierarchies remain intact below the organized root page.

Only a page whose canonical parent is `workspace` may have a folder id. Moving a nested page into a folder atomically promotes it to the workspace, hides its paired `child_page` block, and assigns the folder. Moving a folder page under another page clears its folder id and creates or restores the paired child-page block. Moving it to the project root clears only its folder id. Cross-project folder placement, folder self-parenting, and folder descendant cycles are rejected at both the command and database boundaries.

The project Notes explorer and note picker render a mixed tree with folders first at each folder level and the existing page tree beneath each placed root page. Folder and page expansion are independent local UI preferences. A folder can be closed while one of its notes remains selected and open in the editor. Title filtering matches both folder names and page titles and reveals matching ancestors. Empty folders stay visible outside filtered results. Creating a note from a folder places it there immediately; creating a subfolder keeps it in the same project. Folder creation and folder or note renaming edit the name directly inside its normal explorer row with the applicable icon, transparent field, and soft editing tint instead of replacing the row with a bordered text box. The submitted name remains visible while persistence completes and reverts only if saving fails. Rename fields keep text undo and redo separate from note editor history. Continuous typing and continuous deletion are each coalesced into natural undo steps, while a pause, a change between insertion and deletion, or new input after undo starts a separate step.

Deleting a folder is deliberately non-destructive. Its direct pages and child folders move to the deleted folder's parent, or to the project root when the folder was already at the root. The command deletes only the organizational container and never archives, trashes, or permanently deletes a note. Folder placement is included in JSON graph export and project version history. Notion imports continue to create pages and page nesting, not Ganbaru folders, because Notion has no equivalent folder object.

The Notes top bar is project-level chrome. While the project explorer is expanded, it shows only the selected group and project names. When the explorer is collapsed, it appends the selected note's full folder, subfolder, and parent-note path. One chevron appears only after the final visible breadcrumb segment, immediately before New note. Hover navigation follows the same sibling-level pattern as the Group and Project navigator instead of reproducing the expanded explorer tree. Hovering a current path segment opens the full level containing that folder or note, including its sibling folders and notes. Hovering a row with children then opens the next level containing only those direct children. Empty folders also open their empty next-level panel. Every note hierarchy panel includes its own search field and a split creation footer with New folder, a vertical divider, and New note. The footer omits visible shortcut text. New folder creates at the project root or inside the current folder and opens an inline naming field before saving. New note creates in the panel's project root, folder, or parent note. Note-child panels omit New folder because the data model does not allow folders beneath notes. These panels do not apply a persistent selected style to the current note. The top bar also holds new note creation and project notes settings. Below it, the normal workspace uses a persistent project-scoped explorer on the left and the primary note editor on the right. The explorer uses the same background as the note editor, without a divider line between the two surfaces. It starts with left-aligned compact icon actions for creating a note, creating a folder, sorting, toggling full-tree expansion, searching, and collapsing the explorer, followed directly by the selected project's folders and notes. The toolbar uses the same leading inset as the explorer rows. Collapsing the explorer smoothly reduces its clipped outer width so the note editor reclaims the space while the mounted explorer content stays stable. The collapsed state leaves a narrow rail with a right-facing chevron control that restores the full sidebar. The expansion toggle offers Expand everything whenever any folder or expandable note remains closed. Once the whole tree is open, it changes to Collapse everything. Sorting offers name in both directions, modified time in both directions, and created time in both directions. Folders remain before notes at each hierarchy level, and the chosen ordering applies independently within both types without flattening the tree. Folders are open by default, including newly created and empty folders. Folder and note rows in the persistent explorer have no disclosure chevron or reserved disclosure column, but retain a consistent small leading inset. Closed and open folder icons communicate folder state, and clicking a folder row toggles that state. Empty folders do not render a placeholder or creation row, so opening or closing one changes only its folder icon and collapsed state. New notes remain available through the explorer toolbar and the folder's right-click action. Folder icons and unselected folder and note names inherit the normal row text color. Explorer folder and note icons use the same stroke weight as its toolbar icons. Notes without a custom icon use the default note icon with the same color and stroke weight. Folder and note rows have no overflow buttons. Right-clicking a row opens its viewport-clamped context menu with the applicable create, favorite, rename, duplicate, move, archive, Trash, or delete actions, and the row keeps its hover highlight until that menu closes. Archive and Trash remain in project Notes settings instead of being duplicated as explorer-level destinations. Selecting or creating a note from this explorer replaces the primary editor content. The selected note uses slightly stronger text without a persistent row background. It does not use a peek mode. An empty explorer and an editor without a selected note remain blank. At widths that cannot fit both surfaces, the persistent explorer hides and the existing top-bar note navigator provides the same navigation without resetting selection or editor drafts.

Folder and note rows support whole-row drag and drop with a compact row preview. Explorer dragging moves notes into folders or to the project root. A note row acts as drop space for its containing folder or the project root and never creates a nested note. Dragging a note onto the open editor content is the separate gesture reserved for nesting it under that note. Folders can move into other folders or to the project root. Starting a drag does not select or open the dragged note. Self, descendant, cross-project, and unchanged destinations are rejected before persistence. A valid new destination uses the soft blue selection highlight, while the current or another unavailable destination uses a neutral gray treatment instead of a destructive color. A folder destination highlights its complete visible subtree as one continuous area, whether the pointer is over the folder row or any note within it. Nested folder destinations limit this treatment to their own subtree. The project root does not highlight an unrelated row. Closed folder targets open after a short hover, and wheel, trackpad, or edge dragging scrolls the tree. While dragging, a sticky project-root destination remains available at the bottom of the explorer. A move uses the same validated persistence commands as the context-menu move actions.

Explorer and top-bar creation actions share an active folder location. By default, the location follows the folder containing the selected note, including the root folder ancestor of a nested note. Clicking a folder makes that folder the active location for the explorer New note and New folder actions. Clicking blank explorer space resets the location to the project root. Selecting a note restores its containing folder as the location. The top-bar New note action and the Notes keyboard shortcut use the same active location.

The Highlight current file explorer action expands the selected note's folder and page ancestors. If its row is outside the visible explorer area, the action smoothly scrolls it into view before identifying it with two short soft accent transitions. A row that is already visible begins highlighting immediately.

The settings button opens the same anchored, responsive settings panel pattern as the Projects tab, with a title that identifies the selected project by name. The panel's Appearance section can inherit the global contextual note opening mode or override it for the selected project with center peek, side peek, or full page. This preference applies when a note, subpage, database row, mention, or local note link is opened from inside the current note. It does not control ordinary explorer navigation. The nullable project override is stored on the project row, so existing projects and the Use global setting selection continue to follow the global preference. A separate Restore section breaks from the normal label-and-control row. It contains the compact Version history retention selector, followed by left-aligned Version history, Archived notes, and Deleted notes buttons. The retention selector inherits the global Notes value unless the project stores an off, 7, 30, 90, 180, or 365-day override. The 365-day selection warns that it may use more local storage, including when a project inherits that effective value. Contextual note opening and history retention save through one project settings command and participate in the same draft, discard, outside-click, and Escape behavior. Shortening an effective retention period, including turning it off, shows the number of versions and reclaimable local bytes before pruning. Notes settings owns workspace-level Import and Export actions so bulk data transfer stays with configuration and recovery controls.

Contextual center peek keeps the primary note visible behind a modal. Contextual side peek keeps the explorer visible and splits the editor region between the primary note and the opened note. Full page promotes the opened note into the primary editor and updates the selected explorer row. Peek modes expose a direct full-page expand control plus a one-step toggle between center and side peek. Only the primary full-page note is named in the top bar; peek modes leave the top bar on the primary navigation context. Center peek keeps its normal modal width while side margins shrink, then keeps a compact modal width for snapped half-screen windows before falling back to full page at narrow widths. Its backdrop starts below the global titlebar and Notes top bar, then fills the remaining window including the side and bottom app frame. Blank root pages, folder pages, and page-parented subpages use optimistic creation. Title changes, block saves, and structural mutations wait behind that page's creation barrier and flush in order after persistence succeeds. The authoritative response updates canonical metadata without replacing an active title or block draft. Leaving the provisional page prevents a later response from reopening it or taking focus.

If creation fails, the draft remains open with its generated ids and a retry action. Retry sends the exact original request. The create command treats an exact repetition of an already committed page and initial block as success, which recovers safely when the frontend could not determine whether the first response completed. Reuse of either id with different page placement, title, properties, initial block ownership, type, payload, or ordering remains an error. Missing or partial rows are never accepted as a successful retry.

## Project version history

Project version history is a complete Notes time machine for one project. A version includes the project's folders and page folder placements, page closure across active, archived, and deleted states, nested pages, blocks, databases, data sources, row properties, views, database templates, comments and anchors, comment read state, suggestions, mention notifications, aliases, and managed asset references. It excludes project identity, global templates, Notes preferences, undo stacks, history tables, collaboration operation logs, and rebuildable indexes or caches.

During continuous editing the persistent dirty coordinator creates a checkpoint after ten minutes. It creates a final checkpoint after two minutes without another edit. Before the first canonical mutation for a project, the backend creates its baseline in the ordered mutation workflow, including the empty baseline needed to recover the first created note or folder. Merely selecting a project or opening Notes never creates a baseline. Dirty records survive restarts. One app-level lifecycle scheduler reads the authoritative next dirty and maintenance deadlines at vault activation, wakes at the earlier deadline, and catches up on vault switches, resume, and shutdown. Mutations update the scheduler directly, so no tab-owned polling interval is required. Destructive changes and imports create a complete safety version and force the resulting state to checkpoint immediately. A checkpoint whose manifest matches the latest version is skipped. Retention and orphan maintenance run at most once per vault every six hours. A maintenance transaction prunes all projects first and performs global bundle garbage collection once, while explicit retention changes prune their target and collect once. Opening an empty Notes tab executes no project-history command or project-history SQL statement.

The Version history button closes project notes settings before opening a large modal. If the settings draft has unsaved changes, the existing discard confirmation must succeed before the panel closes and version history opens. Clicking outside the modal or pressing Escape closes it. On wide layouts, the left side reproduces the selected version of the normal project Notes view with its usual background and navigation, but without editing controls. The right side has a sticky Version history heading, keyset-paginated entries showing only localized date, time, and author, and a sticky Restore action. Loading is exposed to assistive technology without adding visible loading copy. Compact layouts use a full-screen version list followed by a preview with a visible Back action and sticky Restore button. Selecting a note lazily loads its historical page, blocks, databases, data sources, and views without mounting editor controls or the live Notes store.

Restore preview reports notes that will be removed, recreated, changed, or copied. Confirmation creates a complete safety version, applies canonical changes in one SQLite transaction, suppresses historical notifications from future delivery, and rebuilds derived indexes only after the canonical transaction succeeds. Notes created after the selected version leave the restored project but remain recoverable through the safety version. If a historical note now belongs to another project, that current note stays untouched and the historical graph is restored as a copy with fresh internal ids. Collaboration operation sequence rows are never rewound or deleted. Restore appends new operations for restored comment and suggestion state.

Nested blocks are represented by parent rows, not by embedding children inside JSON. Lightweight outlines contain block and parent ids, type, sibling order, child presence, and retained height without content payloads. Sidebar refreshes reuse the bounded workspace shell instead of reloading every page and folder. Database templates are scoped to one local data source. Creating a template from a row snapshots that row's editable properties and loaded body block tree into canonical SQLite rows. Applying a template creates a new row page under the data source, remaps the stored block ids, copies body blocks into `notes_blocks`, derives the title from the requested row title, and replays stored properties against the current schema by property id so renamed properties still apply. One default template can be set per data source. Templates are exposed in the table view creation controls, and using no explicit template falls back to normal blank row creation.

Database button properties are local typed actions, not arbitrary automation blobs. The first supported action updates a property on the current row only. Button properties are rendered as derived read-only cell values, not stored row properties, and clicking a button routes through a Tauri command that reloads the current schema, validates the target row, requires confirmation when the button configuration asks for it, then applies the typed property update. Broad actions, destructive actions, webhooks, mail, and third-party integrations stay unavailable until each action family has a local schema, confirmation boundary, and tests.

Page roots, column lists, tables, and tab label layers are protected from invalid keyboard moves before the Rust command boundary.
Undo and redo record snapshot pairs at the same mutation boundaries as normal block commands. Frequent typing, Enter, and paste operations capture only affected blocks, while broader structural commands can capture page scope. Focus or selection changes without a content or structure change do not create invisible history entries. Typing and text-like repeated updates are grouped by block within a short time window. Consecutive Enter actions under the same parent accumulate every created row into one undo transaction, so undo returns to the state before that input burst. Formatting, links, mentions, equations, paste, other structural block edits, template use, and button use remain discrete entries. Snapshot pairs preserve the focused block and its text selection, so undo restores the caret or selection before the edit and redo restores its resulting position. Undo and redo update the local block tree immediately, reserve repeated shortcut actions synchronously, then persist their ordered mutations in the background. The per-page recovery stack is bounded by both entry count and serialized UTF-8 byte size, drops the oldest entries first, and never turns an optional undo recovery failure into a page load failure. Per-block saves are ordered, and a save acknowledgement replaces local state only when no newer local revision exists. Applying an entry reuses existing block rows through update, trash, restore, and move commands. Every page mode constrains the editor to the available height and gives long content to one internal vertical scroll viewport. Focus recovery scrolls that viewport directly and ignores stale focus requests from earlier rapid edits.
The editor surface is split between the page shell, block list, block row chrome, text editor controls, card-like block editors, and media or layout-specific child components. The Notes store keeps its public API stable while delegating page preference persistence, focus request tokens, block tree selectors, debounced block persistence, undo state, and block actions to focused helper modules.

Comment and suggestion writes also append local collaboration operation rows inside the same SQLite transaction as the canonical change. Comment thread creation, comment creation, and suggestion creation are append-only operations. Comment body edits use last-writer-wins operation metadata for the future sync layer because the current local editor has no multi-author rich text merge for comment bodies. Comment deletion, thread resolve or reopen, and suggestion accept or reject are state-transition operations with a base version and resulting entity version. Future sync replay must reject or surface conflicts when the stored base version does not match the local entity version, rather than silently applying stale decisions. Per-user comment read state remains local UI metadata and is not recorded in the collaboration operation log.

Notes navigation is planned from lazily loaded active page metadata, project folders, local expanded-page metadata, and local collapsed-folder metadata. Project-owned pages store the selected project id in local page properties when created from the project home, top bar create action, folder action, or project-scoped note picker. The top bar note picker and cascading project note flyout show only folders and pages owned by the active or hovered project. The project-level home uses the same project scope with a normal in-page surface. Favorites and recents remain local metadata for future navigation surfaces, but they are not shown as separate sections in the current project-level home. Archive and Trash keep their own title filters over recoverable pages. Rows whose parent page is missing or in Trash show a warning state instead of silently pretending the page is a normal root. Archive restore rows and Trash restore or permanent-delete rows remain reachable at the app's smallest supported window widths.

- [ ] Duplicate: duplicate one block from the handle menu, then select multiple adjacent blocks and press Ctrl or Cmd+D. Copy link and color actions keep the menu open for feedback or repeated color changes; structural actions close it and return focus through the editor's normal operation targets. Delete uses the same undo-backed block operation as keyboard deletion, so the user can recover it with page-local undo.

Multi-block selection is page-local UI state over the currently rendered block rows. Pressing Escape from a focused block selects that block; Shift plus Up or Down expands the selected range through the rendered order; Shift-click extends an existing range; dragging from the block handle rail selects the rows crossed by the pointer. Selected rows keep their state while the editor scrolls because the range is stored by block id. A selected-block toolbar and keyboard shortcuts support copy, cut, paste, duplicate, sibling move, and delete for selected ranges. Ctrl or Cmd+X stores the same internal block clipboard, then trashes the selected root subtrees through a Rust transaction. Ctrl or Cmd+V pastes the internal clipboard after the focused block by duplicating the stored source subtrees through a Rust transaction. Ctrl or Cmd+D duplicates the selected root subtrees in place. Delete or Backspace trashes the selected root subtrees. Ctrl or Cmd+Shift+Up and Ctrl or Cmd+Shift+Down move selected root siblings as a group when all roots share a parent and the move target is valid. The backend rejects cycles, invalid parent shapes, duplicate ID maps, and insertion anchors inside a moved subtree. Nested children move or duplicate with their selected roots, rich text payloads stay canonical, block comments stay attached when blocks move, and duplicated blocks receive duplicated block comment threads.

Moving a block up or down reorders it inside its current sibling group through the same Rust move command used by nesting and outdent. Dragging a block from its handle uses a pure move planner before it crosses the command boundary. Valid before and after drops show a thin line, valid nesting highlights the target block surface, and valid outdent shows the line at the destination parent depth. The planner rejects cycles, table rows, columns, invalid parent shapes, current-page page moves, child-page self moves, and loaded descendant page targets before showing a destination. The store flushes pending block saves before every drag-backed structural move, then persists the new parent and adjacent block position through the Rust move command. After the move, the source page reloads so the removed block disappears and the page list refreshes edited timestamps.

Managed local file objects in files properties are tracked through `notes_asset_references`, so imported or programmatic row data does not leave unowned local paths behind. List rows keep the title first, show selected properties compactly to the right, and can be grouped by locally groupable properties without changing row page storage. Calendar rows use a selected date property, filter rows by overlap with the visible month range, display date ranges on each covered in-month day, and create row pages from day cells with that date property prefilled. Timeline rows use a selected date property, filter rows by overlap with the visible range, render horizontal date spans, support optional grouping by locally groupable properties, create rows from date headers, and resize row ranges through date inputs that write the same canonical date property value as table cells. People and relation-shaped groups can be displayed when data already has those values, but drag writes stay disabled until local people editing and group-safe relation writes exist. Text, rich text, number, checkbox, select, multi-select, status, date, URL, email, phone, place, and relation cells are editable in this first slice; files, people, created time, created by, last edited time, last edited by, and unique ID cells are read-only in table editing, while rollup and formula cells are read-only computed outputs. Row pages participate in page search, page duplication, Trash, restore, and permanent deletion through the existing page lifecycle. Database item templates remain planned as a later database slice.

Favorites and recents are local navigation metadata stored outside the canonical page graph. Favoriting a page pins it in Notes navigation and shows a star in the note action bar and navigation row. Opening or creating a page records it in recents so frequently used pages stay reachable without changing page parents, page sort order, or block content.

Notes search queries canonical SQLite data through the `notes_search` command. Results include active page title matches, page alias matches, active block plain-text and rich-text-derived matches, non-deleted page discussion text, block comment text, inline comment text, comment attachment matches, managed file caption and file-name matches, supported metadata matches, and active database row pages whose properties match. Resolved comment threads are hidden by default and can be included from the search results filter. Comment results show page discussion, block comment, or inline comment context with author display metadata and open or resolved state; inline comment results also show their stored anchor text. Database property search indexes text and rich text properties, select and status labels, date ranges, checkbox values with checked and unchecked terms, relation target titles, cached rollup values, and safe formula outputs from the Rust formula evaluator. Rollup matches are included only when a row's rollup cache has been populated by a database read; search does not make rollup values canonical. Formula runtime errors are not indexed as successful formula output. Page and alias results open the page, block results open the page and focus the matching block, relation-derived page results open the source row page, page discussion results open the page comment surface, and block or inline comment results focus the commented block when the thread target still exists. Search uses the rebuildable `notes_search_index` and `notes_search_fts` projection instead of live `LIKE` scans. `notes_search_index_state` fingerprints source tables and rebuilds the projection when source data, data source schemas, rollup cache rows, assets, aliases, or relation facts change, and `notes_rebuild_search_index` can force a repair rebuild without changing canonical page, block, comment, property, or file rows.

Duplicating a page copies the source page row, page icon, cover, visible block tree, and nested child pages through one Rust transaction. The duplicate gets fresh page and block ids, does not inherit import provenance, and keeps child-page block ids paired with their duplicated page rows. Workspace pages duplicate beside the source in the same folder or at the project root. Nested pages duplicate beside the source child-page block in the same parent. Database row pages duplicate under the same data source, preserve row property values, and skip child-page block creation because the database view is their visible navigation surface.

Page templates are global Notes templates modeled after reusable Notion page templates, not database-scoped or repeating templates. Creating or updating a template snapshots the current page's properties, icon, cover, and root block tree into `notes_page_templates` and `notes_page_template_blocks`. Applying a template creates normal `notes_pages` and `notes_blocks` rows through a Rust transaction, sets the applied page title when the user supplies one, and leaves the template rows unchanged. Renaming, duplicating, and deleting templates affect only the template records. Child-page template blocks create paired local child pages with default empty bodies in this first slice; full subpage body snapshots remain future work.

Page history is a local recovery surface for Notes pages. Mutations that change page details, page placement, archive or trash state, child-page links, or block content record a deduplicated snapshot of the affected page before the mutation commits when history is enabled for that page. Rapid editor mutations, including normal block text edits, Enter-created rows, and immediate empty-row cleanup, coalesce into one short edit-session checkpoint instead of creating a separate version for every debounced write. A later edit after the idle window records a new checkpoint. Each snapshot stores the local author id. The page action opens the same responsive Version history modal shell used by project history, scoped to the current note. Its left side renders the selected snapshot as the normal note view without editing controls. Its right side lists only localized date, time, and author, with Copy blocks and Restore kept in the sticky footer. Copying from a version appends fresh block rows to the current page and creates paired child-page rows for copied child-page blocks. Restoring a version saves the current page to history first when history is enabled, then replaces the current page's title, properties, icon, cover, trash/archive flags, and page body blocks with the snapshot. Restoring does not move the page back to an old parent; page location stays under the current page graph so a history restore cannot unexpectedly move navigation context. Child page bodies keep their own page history, while restored or copied child-page link blocks create paired local child pages with default empty bodies when a matching active child page is missing. The effective shared or project-specific retention applies to both page and project history. Turning history off prunes retained versions after confirmation and suppresses new snapshots and checkpoints.

Moving a page changes the page parent through a Rust transaction and keeps the paired child-page block synchronized with the destination. Moving under another page creates or restores the paired child-page block at the bottom of that destination page. Moving back to the workspace hides the paired child-page block so the page becomes a top-level navigation item. Page row actions use the same searchable destination picker shape as block moves, including recent destinations, nested context, search, and keyboard navigation. The picker excludes the current parent where practical, and the command rejects block parents for the navigation move action, missing or inactive destination pages, moving a page under itself, and moving a page under a descendant reachable through page parents or child-page blocks.

Archived pages keep a separate `archived` state in SQLite and are hidden from the normal page list, favorites, recents, active Notes search, active page loading, active parent validation, and parent-page document body without entering Trash. The page action menu confirms before archiving a page. The top bar exposes an Archive view that lists archived page metadata, supports local search, and unarchives a page through the Tauri command boundary. Unarchived pages are selected and loaded immediately. If an unarchived page's stored parent is missing, archived, or in Trash, the page is promoted to the workspace and the stale paired child-page block stays hidden. Trashing a page clears its archive state so Trash remains the single recovery surface for deleted pages.

Breadcrumb blocks use the public Notion `breadcrumb` empty payload shape. The rendered path is generated from the current local page graph instead of being stored as duplicated text, so nested pages update breadcrumbs automatically when page titles or parents change. Breadcrumbs use the backend-resolved page chain for loaded and unloaded ancestors, keep active ancestors clickable, and label archived, trashed, or missing ancestors without opening them through the active editor path. Users can create breadcrumbs from the slash menu or convert existing blocks to breadcrumbs.

Table of contents blocks use the public Notion `table_of_contents` payload shape with block-level color. The rendered heading index is generated from the current local block graph instead of being stored as duplicated text, including heading levels 1 through 4. Users can create a table of contents from the slash menu, convert existing blocks to it, and use generated entries to focus the matching heading block.

Column list blocks use the public Notion `column_list` empty payload shape. Column blocks use the public Notion `column` payload shape with optional `width_ratio`. Ganbaru AI stores columns as internal child blocks under the column list, and the editable content inside each column remains normal child blocks in SQLite. The editor renders the column list as one layout surface, hides internal column container blocks from the main page flow, stacks columns when the layout no longer fits, and keeps keyboard deletion and merge behavior scoped to the focused column. Users can create a default two-column layout from the slash or plus menu, add columns up to the local practical control limit, remove columns while moving their child blocks into a neighboring column, move columns left or right, resize columns through persisted width sliders, and drag existing blocks into a target column drop zone. Nested child block subtrees stay attached to their blocks during column moves and removal cleanup.

Table blocks use the public Notion `table` payload shape with `table_width`, `has_column_header`, and `has_row_header`. Table row blocks use the public Notion `table_row` payload shape with `cells`, where each cell is a rich text array. Ganbaru AI stores rows as normal child block rows under the table block, but the editor renders them as one table surface instead of exposing row blocks as standalone document rows. Users can create a default local table from the slash menu, edit cells through rich-text-preserving contenteditable cells, navigate cells with Tab, Shift+Tab, Enter, Shift+Enter, and arrow keys, and add or remove rows and columns with table controls. The table keeps header flags while local width changes, remains horizontally scrollable at narrow widths, and leaves database-style table views to later P2 database work.

Tab blocks use the public Notion `tab` empty payload shape. Direct children of a tab block are paragraph rows that act as tab labels; their rich text stores the visible label, their optional paragraph icon stores the tab icon, and their child rows store the tab panel content. The editor renders the tab block as one layout surface, hides label paragraphs from the main page flow, and shows the active tab's child blocks as normal editable Notes content. Users can create a default local tab group from the slash or plus menu, rename the active tab inline, choose supported emoji or native icons, add tabs up to the local practical control limit, remove tabs while moving their child content into a neighboring panel, move tabs left or right, and drag existing blocks onto tab triggers to move them between panels. Nested child block subtrees stay attached to their blocks during tab moves and removal cleanup.

Image, video, audio, file, and PDF blocks use public Notion file object source shapes. Ganbaru AI supports editable external HTTPS file URLs for new local blocks, validates imported Notion-hosted `file` and `file_upload` source objects, and lets users choose local files for block attachments. Chosen local files are copied under `assets/notes/files/` with content-hash file names, recorded in `notes_assets`, referenced from `notes_asset_references` with block ownership, and stored in block payloads as `ganbaru-asset:` file objects with metadata instead of raw filesystem paths. Non-empty external URLs must match the block kind, such as image extensions for image blocks, audio extensions for audio blocks, video extensions or supported YouTube URLs for video blocks, `.pdf` for PDF blocks, and any HTTPS URL for file blocks. Local attachments validate managed paths, MIME category, positive size, and SHA-256 metadata before crossing the SQLite command boundary. Import-safe file handling exposes the same storage checks to future Markdown, HTML, and Notion export importers, with diagnostics for skipped references, blocked external URLs, missing import roots, import-root escapes, unsupported target types, and oversized files. The editor keeps local drafts while users type, explains invalid URL, non-HTTPS URL, unsupported type, local attach, and preview states, stores captions as rich text arrays, supports optional file names, and derives the plain text cache from captions and source identity. Managed local image, video, audio, and PDF assets render native previews from local data URLs when the file is below the preview cap, while generic managed files show metadata. Preview loads are deduplicated and byte-bounded, and a preview releases its cached URL when it leaves the rendered retained range. External URLs, imported Notion-hosted file URLs, and imported file upload ids render as explicit reference placeholders with source-state text and never auto-fetch network previews; users open them only through the open action. Users can replace or remove a managed local file from the block without deleting the asset row, so deduplication and recovery remain possible. Caption and display-name edits preserve imported `file` and `file_upload` source objects unless the user supplies a replacement external URL or attaches a local managed file. Missing local asset reads show a local preview unavailable state and mark the managed asset row missing until a later successful read marks it available again.

Bookmark blocks use the public Notion `bookmark` payload shape with a URL string and caption rich text array. Ganbaru AI stores and edits the URL and caption locally, derives the plain text cache from both fields, and does not fetch remote preview metadata automatically. The open button launches only HTTP and HTTPS URLs through the platform opener.

Link preview blocks use the public Notion `link_preview` payload shape with a URL string. Public Notion integrations can retrieve these blocks but cannot create or append them through the public API. Ganbaru AI still supports local creation because Notes are not a hosted Notion connection: it stores and edits the originally pasted URL, derives the plain text cache from that URL, renders a local card from URL parts only, and avoids automatic remote metadata fetches. The open button launches only HTTP and HTTPS URLs through the platform opener.

Synced blocks use the public Notion `synced_block` payload distinction between originals and duplicates. Original synced blocks store `synced_from: null` and can own normal child block rows in SQLite. Duplicate synced blocks store `synced_from.type: "block_id"` with a source block id and render as visible reference placeholders. The editor clearly labels original and duplicate shapes, preserves imported references, keeps duplicates from exposing editable child rows, and leaves move, duplicate, comment, copy-link, delete, and page move as local block operations. Fanout editing across synced copies is not supported yet because the public API does not support synced block content updates and Ganbaru AI has not introduced an independent local sync graph for this block type. Creation from insert menus remains unavailable until local duplicate creation semantics are designed.

Template button blocks use the public Notion `template` payload shape with a rich text title. Their reusable content remains normal child block rows under the template block, not embedded child JSON in the payload. The editor renders a template control strip above the rich title editor with reusable child count, an add-content action that appends an editable paragraph child under the template, and a use action that duplicates the loaded child subtrees below the template through the existing duplicate and move commands. Child-page descendants intentionally disable the use action with visible messaging because page duplication and page link pairing need separate semantics. The public Notion API no longer supports creating template blocks, but Ganbaru AI keeps local template block creation because the local SQLite block graph is the source of truth and no Notion service is involved.

Button blocks use a Ganbaru AI local payload because Notion's public block API does not expose a supported `button` payload even though the Notion product supports page buttons. The local payload stores a rich text label, an optional icon, and a bounded action list. The first supported action is `insert_blocks`, which duplicates the loaded child block subtree from under the button to the configured target position. New local buttons default to inserting below the button. Button action children remain normal child block rows in SQLite. The editor renders a button control strip above the rich label editor with a source child count, native icon and icon-color controls, an insert-position selector, an add-source-block action, a run button, and disabled broad-action choices for unsupported database edits, webhooks, and destructive automations. Users can edit source content as normal child blocks under the button. Child-page descendants intentionally disable the run action because paired page creation and page-link duplication need separate semantics. External actions such as webhooks, mail, Slack, broad database edits, and destructive automations remain unsupported until they have explicit local schemas, user prompts, and permission boundaries.

Embed blocks use the public Notion `embed` payload shape with a URL string. Ganbaru AI stores and edits the URL locally, derives the plain text cache from the URL, and renders a local hostname label instead of fetching remote preview metadata. The open button launches only HTTP and HTTPS URLs through the platform opener.

Equation blocks use the public Notion `equation` payload shape with a KaTeX-compatible expression string. Ganbaru AI stores and edits the expression locally, derives the plain text cache from the expression, and renders a dependency-free formula surface until a vetted math renderer is approved.

Unsupported blocks use the public Notion `unsupported` payload shape and preserve the informational `block_type` string from imports when present. Ganbaru AI also allows validated local provenance fields, raw source metadata, and import warnings in the payload so future importers can avoid silent data loss. Notion documents `unsupported.block_type` as informational only; it is a plain string rather than a fixed enum, and unsupported block content is not exposed by the public API. The editor renders unsupported blocks as visible placeholders with imported type, optional source type, full warning list, and raw payload availability instead of hiding the row. Search text includes the imported type, source type, warnings, and raw-payload preservation state. Users can still duplicate, delete, or deliberately convert the block through normal block handles or the placeholder conversion controls. Conversion is explicit because it replaces the unsupported payload: summary conversion creates a paragraph with visible metadata, while JSON-code conversion writes the preserved raw payload or fallback metadata as editable text for review.

Block colors use the public Notion color names stored in the block payload. Text edits, to-do toggles, toggle open state changes, callout edits, table of contents color changes, conversions between color-capable block types, and duplication preserve the selected color. Rust and TypeScript validators reject unsupported color names before they are treated as typed Notes data.

Trashed pages keep their `in_trash` state and `trashed_time` in SQLite and are hidden from the normal page list and Archive. Trashing or restoring a page applies to the reachable page subtree so child pages do not remain active under a trashed parent. Directly trashing a nested page also hides its paired child-page block from the parent document, and restoring it reveals that block only when the original parent is still active. The top bar exposes a Trash view that lists trashed page metadata, supports local search, restores a page by setting `in_trash` back to false through the same Tauri command boundary, and permanently deletes a trashed page after confirmation. Expired Trash cleanup permanently deletes notes after 7 days in Trash and runs automatically when Notes page commands load or mutate Trash state. If a restored page's stored parent is missing, archived, or still in Trash, the page is promoted to the workspace and the Trash view warns about the known parent-in-Trash case before restore. Permanent delete is a local Ganbaru AI recovery action, not a public Notion API operation. It removes the page subtree, paired child-page blocks, and page body blocks in one Rust transaction after confirmation or retention expiry. Restored pages are selected and loaded immediately. Page history retention is configured globally in Notes settings and can be overridden from the project notes settings panel.

## Backlinks and daily or project notes

Daily notes remain planned. Durable project-note membership exists as local page metadata and keeps project note lists scoped to the selected project instead of the whole group or workspace. The Notes shell mirrors the Projects top bar: group and project selection provide context, the note navigator opens pages for the selected project, and the current page tree remains the canonical note source.

Daily and project note categories are conventions over Notes pages, not separate markdown folders and not separate data models.

## Sync and collaboration

Local editing is SQLite first. Future sync can layer CRDT state over the same page and block graph, but it must preserve SQLite as the local canonical store and keep markdown as a derivative format.
