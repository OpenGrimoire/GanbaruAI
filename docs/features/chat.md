# Chat

Chat is Ganbaru AI's communication and coordination workspace. It gives a person durable places to discuss work with human collaborators, persistent AI teammates, and task agents without turning every objective into another isolated assistant conversation. The normal unit of navigation is a channel, direct message, task discussion, or reply thread. A provider session is bounded execution machinery beneath that organizational history.

The complete delegation model lives in [Agent coordination](agent-coordination.md). Provider transports and the broader AI architecture live in [AI integration](ai-integration.md). Security invariants live in [security](../data/security.md). This document defines the user-facing Chat product and the coding workspace that appears when a conversation starts or inspects agent work.

## Product objective

Chat should make the person responsible for intent, priorities, approval, and judgment rather than repetitive prompt supervision. A person can describe an objective to the Ganbaru manager or a project channel, review a structured plan, and later review deliverables. The manager coordinates approved tasks through Projects, Calendar, Notes, and bounded agent runs.

Chat is not the source of truth for tasks, schedules, or durable documents. Projects owns commitments and work state, Calendar owns time and capacity, Notes owns durable knowledge, and Chat owns communication plus provenance. When a discussion creates or changes structured work, the resulting record links back to the originating conversation, participant, reason, and approval.

Ganbaru borrows stable channels, direct messages, participant streams, mentions, replies, and unread state from human communication tools. It does not copy notification pressure, channel proliferation, presence pressure, or the expectation that every message must be read. A person delegates by addressing a persistent AI teammate in the same place where the work is discussed. The resulting shared reply thread contains the request, steering, questions, decisions, status, and result. Detailed provider activity remains available through the linked run without becoming channel noise.

## Vocabulary

- **Channel:** a durable purpose-based room. It can eventually belong to the Ganbaru AI folder, a project group, or one project. The first redesign uses project-scoped channels and creates one `#general` channel per project.
- **Direct message:** a durable conversation with stable human participants or AI teammates. Provider and model changes do not change the participant identity.
- **Task discussion:** a focused conversation attached to one task, its assigned worker, project manager, reviewer, and invited participants.
- **AI teammate:** a persistent participant with a user-facing name, avatar, role, instructions, membership, memory scope, authority, budgets, and execution policy. Its provider and model are replaceable implementation choices.
- **Reply thread:** a focused branch beneath a message. An addressed AI teammate works and can be steered here. The reply thread is part of an organizational conversation, not a provider continuation.
- **Work assignment:** one explicit request addressed to an AI teammate in a channel, direct message, task discussion, or reply thread. It can use several bounded agent runs without becoming several visible chats.
- **Agent run:** one bounded execution attempt with an explicit task or objective, context package, provider, model, working folder, authority, budget, artifacts, and lifecycle state.
- **Provider thread:** the native continuation used by a coding-agent harness. The existing internal Chat thread model serves this execution role and must not define the visible organizational hierarchy.
- **Sidebar section:** navigation-only organization for channels. It does not create a Projects hierarchy level or grant access.

## Participation and invocation

Messages have a stable author plus addressed participants or teammates. Sending an ordinary message stores organizational communication without creating a reply thread or requiring an AI provider. A structured participant mention makes a top-level message thread-capable. The default channel behavior invokes an AI only when the person uses an actionable `@teammate` mention, selects a teammate action, or starts direct agent work. A DM with an AI teammate addresses that teammate by definition.

An actionable AI mention on a top-level message creates one work assignment anchored to that message and opens or continues its reply thread. The teammate acknowledges, asks questions, accepts steering, reports meaningful state changes, and posts its result inside that shared thread. The root channel row shows reply count, participants, and unread state. It does not mirror execution progress or the complete execution transcript into the main channel. A participant may deliberately broadcast a useful reply or final digest back to the channel, but that is not the default.

Anyone who can participate in the reply thread and invoke that teammate may clarify or correct the request. The teammate replans from durable thread messages and explicit context revisions rather than treating the first prompt as immutable. A correction does not create another disposable chat. It updates the existing work assignment or creates a clearly linked follow-up when scope, authority, workspace ownership, or review requirements require a separate run.

The first mention-led slice permits one addressed AI teammate per work assignment. Human mentions may accompany it. Later explicit fan-out can assign different objectives to several teammates, but one message never starts surprise parallel work or multiplies spend merely because several names appear in prose.

Adding a teammate to a channel makes it addressable there. It does not grant code, shell, Notes, Calendar, another channel, or every resource in the same project. Dispatch preflight resolves the requesting participant, destination, teammate identity, context, resource grants, safety policy, and budgets before any provider receives data or starts work. A denied request remains a normal message and receives a permission-safe explanation.

Every Send in an organizational composer persists communication first. A structured `@teammate` mention creates a work assignment, while ordinary messages and plain text that resembles a mention never start a provider. A top-level assignment opens its reply thread automatically. Replies invoke the assigned teammate. Queued, working, and waiting assignments accept continuations. A reply to work that is ready for review completes that reviewed assignment and creates a linked follow-up assignment. Pending continuations remain durable, are delivered in message order when the run starts, and are recovered after restart. A compact per-message control in the thread composer can also share a useful reply with the original channel, and it resets after sending to avoid accidental repeated broadcasts.

The composer clock selects a later delivery time for the next message in a channel or reply thread. Selecting a quick or custom time only arms the composer, so the user can choose a time before writing and can still review the complete message before pressing send. The clock remains highlighted while later delivery is selected, and the normal send action persists the scheduled message. Quick choices cover later today, tomorrow morning, and the next non-duplicate Monday morning. The custom path reuses the shared mini date picker and opens the shared 30-minute time picker as a separate floating panel.

When the current conversation has scheduled messages, a compact summary sits outside and above the composer and reports the count and next delivery time. Its management action opens a scrollable surface where every scheduled item uses the normal local profile name and image, message typography, complete untruncated text, and attachment or resource context. Scheduled items can be sent immediately or cancelled. Failed deliveries retain their error and provide a retry action. Immediate delivery uses an atomic claim against the same durable row as background delivery, so the two paths cannot send the same message concurrently. The scheduling picker does not show an empty management state. Scheduling preserves structured mentions, attachments, resource references, and the optional channel-sharing choice. It does not create a visible message, reply thread, work assignment, provider run, unread change, or channel activity until delivery succeeds.

Scheduled delivery is durable in the active folder SQLite database. While the main app is running, one lifecycle scheduler waits for the exact next database deadline without polling. It catches up after system sleep, focus recovery, active-folder changes, and app restart. Because Ganbaru is local-first and has no remote delivery worker, a message that becomes due while the application is fully closed is sent on the next launch. Repeated delivery attempts reuse one stable command ID, so a retry cannot create a second post after its durable receipt completes. A destination that becomes unavailable retries with a bounded cadence and becomes an explicit failed schedule after repeated attempts instead of silently disappearing or invoking an AI in the wrong place. Scheduled attachments remain referenced until the schedule is delivered or cancelled.

The Ganbaru manager can appear as an available teammate in a project's `#general` channel once a compatible provider is configured. Availability is not permission to process every channel message. Later opt-in subscriptions can perform bounded triage or scheduled digests, but each subscription exposes its trigger, readable scope, authority, frequency, cooldown, and budget. It can be paused, and the UI never implies that an agent is listening when no run will occur.

## Scope

Chat's ideal product scope includes:

- Durable channels, direct messages, task discussions, replies, drafts, attachments, search, archive, unread state, and restart recovery.
- Stable participant and AI-teammate identity independent of provider instances and model sessions.
- Reviewable manager plans that can propose tasks, subtasks, dependencies, acceptance criteria, assignments, reviewers, estimates, deadlines, budgets, risks, and Calendar effects.
- Typed links between messages, Projects records, Notes, Calendar events, context packages, agent runs, reviews, and deliverables.
- Automatically discovered local provider instances plus explicitly configured instances for execution.
- Streamed assistant messages, reasoning summaries, commands, file changes, tools, tasks, warnings, usage, and cost when a linked run is inspected.
- Native approvals, structured questions, steering, queued follow-ups, interruption, and force stop.
- Revision-safe file editing, changed-file inspection, inline review comments, run terminals, terminal context, Git checkpoints, source control, optional worktrees, and an isolated browser preview.
- Work-in-progress limits, review-capacity awareness, exception routing, and digest-style progress so parallel agents do not create supervision burnout.
- Wide, compact, detached, increased-font, reduced-motion, keyboard, screen-reader, and minimum-recovery layouts.

The current implementation provides project channels, provider-free messages, reply threads, persistent AI teammates, membership-scoped folder grants, durable assignments, inline exact-run execution activity, and local coding workspace tools. Automatic manager planning, task spawning, functional direct messages, human membership, permission-aware sync, remote clients, mobile continuation, a general BYOK assistant, and hosted execution remain later layers. Local branch publication, pull-request automation, and browser preview belong to the coding workspace.

## First use

Every active project owns one durable `#general` channel. Project creation creates that channel without requiring an AI provider. The channel rail treats this as a project invariant and shows a stable loading row until the durable channel query finishes, rather than briefly presenting an empty channel list. `#general` cannot be renamed or archived. The pre-release redesign intentionally has no legacy provider-thread migration or compatibility fallback because no user-capable release stored the earlier development data. Development vaults are reset instead of guessing which unrelated sessions belong together.

On the first Chat load for a vault in each app session, Ganbaru runs one bounded discovery pass for every implemented provider family that is not configured or explicitly opted out. Initial Chat readiness includes this pass: provider-dependent settings and teammate drafts do not mount from the earlier incomplete settings snapshot. It checks each family's known command names on the application path and conventional user CLI directories, including standard pnpm, npm, Bun, Cargo, and Volta locations. When it finds an installed CLI, Ganbaru creates a default instance with the resolved device-local executable path, reuses the CLI's normal home and existing authentication, probes its status, and caches its model catalog when available. Refresh all repeats discovery for newly installed families, then updates the health and available model catalog of every configured provider. Native catalog metadata remains authoritative: Ganbaru preserves stable raw IDs while showing resolved versioned names and only exposing effort levels and speed modes reported for each model. A person who already installed and authenticated a supported provider can select a project, open `#general`, and address an available AI teammate without configuring a path. Root config changes use serialized key-level mutations, so automatic provider creation cannot be erased by a stale preference snapshot written during startup.

Refresh all forces a new discovery pass before it re-probes every configured instance, so a CLI installed after Ganbaru started or after the first Chat visit appears without resetting application data. Opening provider settings starts this refresh in the background. If a configured executable disappeared, probing searches the same known command locations, preserves the provider instance and its advanced settings, stores the replacement path in device-local state, and probes the replacement. An installed CLI with a broken package, unsupported version, missing authentication, or another probe problem remains visible with a recovery status instead of being treated as absent. A command that is genuinely missing is not added.

Provider session startup applies the same recovery when a missing executable is detected. Ganbaru records the unavailable probe instead of retaining a stale Healthy status, searches for a replacement executable, and retries session startup once when a viable replacement is found. The retry does not persist a second message, assignment, or turn. Other launch failures and a second missing-executable failure settle normally without an unbounded retry loop.

If no supported CLI is available, Chat directs the user to provider setup and official installation guidance. The advanced provider setup remains available for additional accounts, custom homes, arguments, environment variables, and credential references. Removing the last instance for a family records an explicit opt-out so later automatic scans do not recreate it. Adding an instance manually enables the family again. The model picker lists unconfigured implemented integrations as setup actions inside the corresponding company subsection even when only one integration is currently configured.

The first-use flow is:

1. Create or select a project. Its managed folder and `#general` channel already exist.
2. Open Chat from Projects or the Chat tab. The shared project and remembered channel are selected without exposing the managed working folder as a navigation category.
3. Write in the channel normally. When a message addresses an AI teammate or starts direct agent work, Ganbaru resolves the teammate or project execution policy and makes the effective provider, model, permission, and working folder inspectable before dispatch.
4. If automatic discovery finds no healthy provider, the channel history remains readable and writable, while AI actions provide a direct setup path instead of blocking the complete Chat surface.

Failed probes preserve entered fields. Missing folders, replaced folder identities, unavailable providers, unsupported capabilities, and another device without a binding have distinct recovery actions. A device binding records the stable filesystem identity of the folder separately from optional Git storage. Normal Git changes do not make Chat, Files, references, or terminals lose the folder. Replacing the bound directory still requires deliberate recovery. Replacing, removing, or corrupting only the Git storage keeps ordinary folder access available but blocks Git-sensitive operations until the user deliberately rebinds the repository. Automatic discovery never supplies credentials, changes the CLI home, installs software, or chooses Full access.

A fresh organizational draft belongs to its channel, direct message, task discussion, or reply thread. Channel and thread drafts, selections, undo state, and scroll positions remain independent. Posting a message or deliberately retrying failed work moves that surface to its latest content. Composer growth keeps the end anchored only when the person was already at the end. Incoming messages and agent output do not move a reader who scrolled upward. Execution preferences resolve from the addressed teammate's immutable policy revision and exact channel membership. The membership supplies allowed folders, exactly one default folder, and the native approval policy. When no AI teammate exists, the channel shows a direct first-teammate setup action instead of relying on discovery through Settings. The guided flow prefers the first healthy provider in OpenAI-first order, its strongest selectable built-in model, Medium effort when supported, the current channel, the project's managed folder, and Ask for approval. Nothing becomes active until the person reviews and saves it.

Chat settings opens on Teammates, followed by Providers, Agent files, and Behavior. Provider connection management and model catalogs share one area because they describe the same configured coding-agent instance. Agent files is reserved for each provider's global configuration and instruction files, while teammate resource grants remain in Teammates. These areas use the same resident settings grammar as Notes, Appearance, and Doomscrolling: text-only area navigation, flat semantic sections, shared selects and switches, thin separators, and entity rows without nested decorative cards. The teammate directory uses a master-detail layout with a compact identity column and one larger editor. Each column scrolls independently within the settings viewport, and the editor keeps its lifecycle and save actions available in a fixed footer without adding a separate footer surface. Directory rows show the avatar, name, and role. Availability stays on the editor name line. The role appears directly below the name in the directory, editor, mention picker, and identity details, replacing handles and generic AI-teammate repetition. Selection uses an inset rounded highlight without a chevron or avatar outline. Adding a teammate creates a visible unsaved draft row after the existing directory entries and scrolls it into view, with a live header preview using the selected avatar, name, role, and availability. Switching Chat areas, switching main Settings sections, or closing Settings while this draft exists opens a brief confirmation before discarding it. Name and role are required. Empty draft previews use the field labels instead of invented identity values. The draft preserves the suggested execution policy separately and presents structured validation errors at the applicable field. A teammate has one user-facing name, which is also its mention label. AI teammate names are unique regardless of capitalization or surrounding spaces across active and archived identities, keeping mentions and history unambiguous. Its immutable participant ID provides internal identity without exposing another user-managed handle. The editor owns stable identity, role, instructions, provider, model, reasoning, speed, options, and channel memberships. It separates identity, execution, and channel access, presents working-folder grants as explicit selection rows, and does not repeat the selected values in a redundant review panel. Save activates only after a valid draft differs from its loaded state.

The teammate directory shows active identities by default. When archived identities exist, a compact pressed-state archive button beside Add teammate can include them in the same list without permanently dividing the directory into separate views. Its tooltip and accessible label describe whether it includes or hides archived identities. Archived rows retain their normal avatar and place a small archive glyph over its lower-right corner instead of adding a separate status column. The wider editor keeps a labeled Archived status. Archiving always requires confirmation, removes the teammate from addressable active work, excludes it from new mention candidates, and is rejected while the teammate owns an active assignment. Existing messages and mentions retain the archived identity's name, provider avatar, and identity details for attribution, but do not make it interactive for new work. Archived teammate settings are read-only until restored. Restore returns the identity, policies, and memberships to active use. Permanent deletion is offered only for an archived teammate that has never authored a message, appeared in a mention, or owned a work assignment. Once any durable communication or work history references the identity, Ganbaru retains it so old conversations and assignments remain attributable.

Provider settings treat integrations as the primary navigation and configurations as children. Every provider family remains visible in one compact tab row whether it is configured, unavailable, healthy, or needs attention. Selecting a family shows all of its device-local configurations as flat rows with explicit selection, health, account privacy, enablement, refresh, edit, and removal controls. A reported account identity shares the Health and Version metadata row. It is hidden by replacing its characters with a deterministic fake value that preserves separators and apparent shape, then lightly blurring only that fake text. The account value itself is the reveal control, its tooltip changes between reveal and hide, and no placeholder is shown when the provider reports no account. The value has no fixed-width truncation and may wrap when space is constrained. When several configurations exist, a bare check beside the name identifies the configuration whose catalog is shown below. A single configuration has no redundant selection marker, and selection never uses a checkbox-like circle. The action after those rows sets up an unconfigured family or adds another configuration for the same family. There is no global Add provider action and configured instances do not replace the provider-family navigation. The selected configuration's model catalog follows the configuration list without a repeated provider heading. Search, custom-model actions, favorite state, and picker visibility operate on that selection. Models are generated directly from catalog entries and ordered by favorites, company, model generation, and capability tier. Rows show a compact name, useful catalog state, favorite state, and picker visibility. The exact ID appears only when it adds provider qualification, alias, version, or other identity information beyond capitalization and separator formatting. Rows do not depend on hand-authored descriptions for known models, and newly discovered models enter the same generic presentation automatically. Opaque capability counts and reasoning defaults do not belong in this list.

Adding or editing a provider opens one scrollable detail editor with the same header, section separators, responsive field rows, shared switches, bordered square icon actions, and fixed action footer as the Doomscrolling limit editor. The provider family is fixed by the family page that opened creation or by the configuration being edited, so the editor never asks the person to select it again. Its contextual title names that family. Canceling or completing the editor returns to Providers with the parent settings context preserved. The form has exactly two permanent sections: Connection, which includes the instance label and provider-specific connection fields, and Advanced settings, which is always visible. Advanced collection labels such as launch arguments and environment variables use the same label and control alignment as scalar fields such as Instance ID. Only the repeated entries beneath them receive subordinate treatment. A new configuration receives a collision-free instance identity automatically. Technical instance IDs, launch arguments, and environment overrides remain under Advanced settings. Provider configurations do not carry decorative accent colors because Ganbaru distinguishes them through labels and connection state. Editing connection details preserves existing enablement, model visibility, and favorites. Project working folders and the primary manual workspace folder belong to Project settings. Rebinding opens at the current folder, or its nearest available parent if the folder moved or was removed.

## Chat shell

Projects, Notes, and Chat share one selected project when the current room is project-scoped. Chat uses one tab-level breadcrumb such as `Group / Project / #channel`. A folder-level or group-level room uses its corresponding scope. A direct message uses participant identity instead of a project path, while a task discussion identifies its project and task. Every breadcrumb segment is a separate navigation target. The group segment opens all groups, hovering or focusing a group opens its projects, and hovering or focusing a project opens that project's active channels. The project segment opens the current group's projects directly and preserves the same project-to-channel sub-panel. The channel segment opens the current project's active channels directly. Project panels retain Projects and Notes behavior for search, inactive-project recovery, creation, menu aim, viewport clamping, keyboard focus, and touch click fallback. Each channel panel has channel search and New channel. Selecting a channel in another project updates the shared project and channel selection without changing the ownership of any existing agent run. Channels use a semantic hash icon rather than a customizable project icon. That icon inherits the current foreground and uses the same compact identity size and stroke weight as group and project icons in the breadcrumb and its navigation panels.

The left explorer sits below the tab header and uses the same minimalist dimensions as Notes: 16 rem expanded and a 2.75 rem restoration strip when collapsed. Its primary organization is communication, not filesystem layout. It shows collapsible Channels, custom sections, a reserved Direct messages section with a generic empty state and inactive add and overflow affordances, and a pinned archive. These section headers share one left-aligned title edge and place their disclosure chevron immediately after the visible title or its truncation ellipsis. The disclosure target continues across the remaining header space until the separate action controls at the far right. Disclosure chevrons remain visible in both expanded and collapsed states. Custom section state and the last selected channel remain device-local presentation state, but every key includes the active vault identity and project identity. Recreating or switching the Ganbaru AI folder cannot expose another vault's section layout. Search uses SQLite FTS across organizational messages and replies independently of loaded pages, and a result opens the exact project, channel, reply thread, and message anchor. The Channels header exposes Add section through its vertical overflow menu instead of rendering a standalone creation row. Section overflow controls use vertical ellipsis icons, while channel actions open from a right-click context menu without a persistent row control.

Channel rows show purpose-oriented identity without live work-progress or unread glyphs. Agent-run progress does not create a new sidebar row unless the person creates a persistent AI teammate or opens the run from its task. Attention moves to the notification model instead of accumulating status symbols beside every channel. The rail provides New channel and, once participant identity exists, New message. It does not expose New chat as an invitation to create another disposable provider session.

Working folders move out of the primary rail. They remain project resources selected through project settings, task execution settings, direct-agent composer controls, and the coding workspace header. A channel can link several agent runs that use different authorized folders. Every individual run and provider continuation remains permanently bound to its project and working folder, so changing a channel's later execution default never retargets existing work. A missing, unbound, or archived folder leaves the channel readable and blocks only actions that require that folder.

The tab header remains present for drafts and active conversations. A channel shows its name, topic, scope, participant avatars, and applicable membership or visibility state. Manage members adds an existing AI teammate to the channel or creates one, then later supports people when collaboration is functional. Human Invite controls remain absent or visibly disabled with an explanation until sync, identity, and permissions work. The header exposes working folder and branch only while direct agent work or an agent-run workspace is selected. One persistent cluster containing bottom dock, inspector, and overflow actions stays anchored to the tab's far-right edge while the inspector opens beneath it and reserves the same space. The right inspector has no separate maximize or close buttons. Its persistent inspector toggle closes it. Rename temporarily replaces the final breadcrumb segment with the existing accessible title editor. The overflow retains Settings, Detach, Archive, and other actions applicable to the selected room or run.

An ordinary channel composer emphasizes message content, channel members, `@teammate` mentions, attachments, formatting, and Send. Its mention picker distinguishes people from AI teammates, shows each participant's stable name, avatar, role, type, and availability, and lists only participants addressable in the current destination. The picker uses the role as the secondary identity line and aligns availability with the name rather than centering it across the row. Pointer movement updates the active row without taking the text caret, while Enter, Tab, and click select the same identity. Selection inserts one atomic mention labeled with the participant's display name plus a trailing space when the mention ends the draft, so typing can continue immediately. Selecting a model is not the same as addressing a teammate. Provider, model, permission, working folder, context usage, and Build or Plan controls appear when the person creates or edits a teammate, starts direct agent work, configures a task run, overrides an eligible thread run, or inspects an execution session. They do not dominate normal organizational communication.

Provider, model, effort, speed, approval policy, and folder grants are controlled teammate-editor fields, not room-composer controls. Each assignment freezes the newest teammate policy and exact membership authorization. Existing runs keep that snapshot. Revoked memberships and folder grants immediately block queued or future execution.

The organizational composer preserves Chat's established rounded card treatment, dimensions, typography, toolbar layout, and circular Send action. It removes provider-specific controls while keeping message content, images, bold, italic, participant mentions, and project file or folder references. Structured mentions receive an identity-colored inline treatment in the draft without changing their plain-text representation, selection offsets, copy and paste behavior, or provider input. The `@` picker is reserved for current channel participants, uses atomic typed mention nodes, remains anchored to the measured caret and viewport-clamped, and exposes configuration health. Its bordered surface does not use a drop shadow. Project file and folder references live in the `+` menu as typed context references. While a thread assignment can be stopped, the colored Send action becomes a square Stop action. Clicking it, or pressing `Ctrl+.` on Windows and Linux or `Cmd+.` on Apple platforms, stops the assignment. The composer remains editable, and pressing Enter continues to post or queue the written reply rather than stopping work. No separate sticky work banner is shown.

When the inspector opens as a desktop column, its body and tab controls participate in a deliberate width transition immediately without opacity effects. The persistent bottom dock, inspector, and overflow action area is an opaque reserved part of the shared header sized to the rendered three-button cluster. The conversation header measures the moving inspector boundary against the actual bottom-dock button. Open folder and branch controls keep the same rendered gap used between adjacent fixed action buttons until they must stop before those actions, avoiding interpolated spacing, clipping, and bounce in either direction. Moving inspector controls pass beneath the fixed action layer instead of visually mixing with those three actions. Inspector tabs share one preferred width while space permits, then shrink evenly down to a compact minimum before the strip uses horizontal scrolling.

The teammate execution editor and direct-agent composer share one compact model control instead of separate provider, model, reasoning, and speed selects. Its summary combines the selected model and effective effort. Opening it shows the capability-driven effort ladder, followed by an Advanced row and the compact Fast action when the provider supports a speed tier. A model without provider-reported effort levels keeps the layout stable with a neutral, disabled five-stop track that has no fill or selection thumb. Advanced reveals Model, Effort, Speed, and any other provider-advertised model options. Those rows open adjacent option panels anchored directly to the hovered row's available side, while Model opens the cross-provider catalog. Moving between effort stops can select the matching lighter model where the catalog defines that relationship. Closing and reopening the compact control preserves the selected overview or Advanced stage but closes its adjacent panel. Opening the model picker leaves the trigger at its natural width instead of expanding it to the panel width. In the teammate editor, Model and Approval occupy the two columns of one Execution row. Both panels prefer opening below their trigger and move above only when the lower space cannot accommodate them. Their controls use the same persistent soft pill surface, rotating chevrons, short directional entrance motion, and shallow panel shadow. Normal effort and approval text and icons use the regular foreground color, while the highest effort and Full access retain their distinct warning treatments. Full access shifts the warning hue toward the destructive signal and then the active foreground on light surfaces, producing a legible orange, while dark mode retains the warning token directly. The model list uses the same scroll treatment as Project settings. It hides the native scrollbar, places the custom track at the panel's right edge without moving row content, scrolls the search field with the list, and fades only the top or bottom edge where additional content remains available.

Favorites remain a flat list without nested subsections or divider lines. Each one-line favorite row places the model company's muted mark directly beside the model name instead of repeating the source as a second caption row.

Company model subsections use capability-oriented catalog order rather than alphabetical, favorite, or recent-use order. OpenAI generations sort newest-first with Sol, Terra, and Luna ordered from strongest to lightest within their generation. Anthropic sorts Opus, Sonnet, then Haiku, with newer versions first inside each family. Speed controls are provider capability-driven. Codex exposes provider-reported service tiers. Claude Opus aliases and versions 4.6 or newer expose Claude Code's Fast mode as a boolean session setting, while Sonnet and Haiku do not. The Speed subpanel presents both Standard and Fast for boolean provider settings instead of making the disabled state implicit. Standard and Fast always include concise explanatory text, using provider descriptions when available and neutral localized fallbacks otherwise. Newly discovered and older cached Claude catalogs receive the same capability normalization, so installing this version does not require a manual provider refresh. Cursor exposes Fast only when its ACP session advertises the corresponding configuration option. Grok and OpenCode do not receive a synthetic Fast toggle because their current provider interfaces do not expose an equivalent same-model latency tier. Ganbaru passes explicit Claude Fast selections through the CLI's managed `--settings` argument and does not confuse lower reasoning effort or a lighter model with Fast mode.

Provider models marked as deprecated are migration hints rather than selectable models. Ganbaru removes them at the shared catalog boundary before returning or caching discovery results, filters older cached catalogs when reading them, and applies the same rule during frontend validation. Deprecated models therefore do not appear in Chat or model settings.

## Teammate setup and membership

Chat has a teammate directory separate from the provider and model catalog. Creating a teammate defines:

- Name, avatar, concise job description, and behavioral instructions.
- Channels and direct messages where it can be addressed.
- Default integration, model, effort, speed, and fallback policy.
- Working folders, Notes scopes, Calendar operations, Ganbaru commands, external connections, and tools it may request.
- Safety and approval policy, including actions it must never perform.
- Token, monetary, time, and iteration budgets plus warning thresholds.
- Memory namespace, retention, and whether approved memory can cross selected channels.
- Optional scheduled or event-driven subscriptions, disabled by default.

The simple path starts from a role template and asks only for the teammate's name, job, primary working folder, and provider. Advanced sections expose the remaining boundaries. The final review summarizes what the teammate can read, change, spend, and publish in plain language before creation. Creating or editing a teammate never authenticates a provider, expands a working-folder binding, or grants a resource implicitly.

Adding a teammate to a channel creates a scoped membership. The member list shows its role, availability, and the resources relevant to that channel without revealing inaccessible resources. Removing it prevents new invocations and proactive subscriptions but preserves legitimate historical messages and run provenance. A stable teammate can use a different provider later without renaming the participant or splitting its conversations.

An AI direct message is the persistent private coordination surface for that teammate. Organizational and personal identity modes remain visibly distinct. An organizational teammate keeps its own scoped principal. A personal teammate can use personal connections only when configured for that mode. Temporary task agents do not automatically fill the Direct messages list.

## Mention-led work threads

An actionable `@teammate` mention is the normal bridge from conversation to execution. Sending the root message first commits it as organizational history. Ganbaru then creates one reply thread and one work assignment, performs authorization and budget preflight, freezes the initial context manifest, and starts the first bounded run only if preflight succeeds. Editing or deleting the root before pickup follows the same cancellation and audit rules as changing any queued assignment.

The thread is a shared coordination surface. It shows the root message, human and teammate replies, questions, approvals, corrections, concise status, results, review packets, and links to deliverables. Any authorized participant can steer the teammate from the thread. New replies become explicit context additions with author, time, and revision provenance. New messages elsewhere in the channel do not silently enter a running assignment. A person can deliberately add another message, file, Note, task, or channel excerpt to a new context revision. A failed assignment shows one compact recovery summary above the thread composer instead of repeating a provider-thread banner beside every embedded agent run. Retrying keeps the visible reply thread and may replace its failed hidden provider session.

On wide layouts, opening the reply count reveals a right-side thread panel without replacing the channel. The panel can expand when the discussion or review needs more room. Narrow layouts use a focus-contained sheet or full conversation surface while preserving both channel and thread drafts. The root message remains visible in the channel with participant avatars, reply count, and unread state, without a live work-progress badge.

Channel and reply-thread unread state counts only messages from another participant after the local participant's read cursor. A person's own messages never create unread state. Opening a reply thread advances its cursor to the latest current item ordinal and clears the root message's unread indicator immediately.

The teammate communicates like a participant through the existing provider timeline presentation. Its final model output is the teammate reply itself, not a second materialized message beside an execution card. The provider mark remains the avatar, and the teammate name is the complete visible author label. Model and effort provenance stays outside the message name. The same provider and model avatar represents that teammate in channel membership, mention choices, reply summaries, organizational messages, and execution history. If the identity is temporarily unavailable, the surface preserves the same avatar geometry and uses a bounded teammate fallback rather than a generic bot icon. Tool calls, raw commands, internal session starts, context compaction, retries, and routine progress remain inside the timeline's existing `Worked for X` disclosure. A provider change, model change, compaction, resume, or replacement run does not create an `AI session` message or divider in the organizational conversation.

One work assignment can link several provider sessions or runs when recovery, replanning, specialization, or workspace isolation requires them. The stable teammate remains the visible author. Run provenance records the effective provider, model, context package, permissions, usage, artifacts, and reason for every handoff. Every visible run loads its exact canonical turn independently and renders its provider rows directly in the reply flow, including runs from earlier provider sessions. Its internal triggering message is suppressed because the durable organizational root already represents that input. The durable projected result remains available for history and search but is not rendered as a duplicate next to the provider result. A thread with exact provider history does not render that projection while the exact run is loading. It holds the transcript in one stable loading state and commits the complete execution presentation once, preventing a plain organizational message from flashing before the rich run UI.

The initial context manifest contains the root request, the bounded channel context necessary to interpret it, existing thread replies, explicitly attached resources, the teammate's role instructions and permitted memory, and the effective grants and budgets. It never means the complete channel transcript or whole project by default. Context used is inspectable by source and revision. Search remains database-backed and permission-scoped independently of which channel or thread pages are currently resident in memory.

Raw reasoning text is never promoted into the conversation. The next real paragraph or action replaces the current transient row, while all earlier real work remains visible.

Every consecutive tool-activity run, including one tool, uses one outer disclosure inside the model turn's process history. A paragraph, plan, or other non-tool timeline row ends the run. No standalone `Used a tool` row appears between organizational participants, and a provider start is not classified as a tool. Opening that live disclosure shows every completed and active tool in chronological order. Each command row retains its own nested terminal disclosure. Only the first phrase is capitalized when several summaries are joined.

Conservative command recognition turns common workspace searches such as `rg`, `grep`, `fd`, and `find` into file-search activity, and common reads such as `sed`, `cat`, `head`, `tail`, and `Get-Content` into file-read activity. Unrecognized commands remain commands, and unrecognized provider tools remain generic tools. Provider titles, exact commands, paths, queries, and tool names remain inside the expansion instead of dominating settled conversation scans. Command details render a typed execution surface with the shell command, working directory, streamed or aggregated output, duration, exit code, and final status when those fields are reported. ## Composer and provider interaction

For an ordinary room message, the optimistic send transition is synchronous after local membership, attachment, and mention checks. Persistence continues after the local user row is visible and the composer is cleared. A failure removes the optimistic row and restores the recoverable room draft. Addressing an AI teammate can persist the message before a manager action starts, so provider startup failure does not erase valid organizational communication.

For direct agent execution, draft persistence, mention revalidation, native dispatch, and provider startup continue after the user row is visible and the execution composer is cleared. If preflight fails before the durable execution message exists, Chat removes the optimistic execution row and restores the recoverable draft.

Organizational composers use destination-scoped controllers keyed by channel or reply thread. Opening a thread never replaces the channel controller. A successful send clears both the visible composer and its persisted destination draft, so remounting the thread cannot restore sent text. Versioned rich content preserves atomic mentions, attachments, resource references, selection, deletion, undo, copy, paste, and IME behavior. Both direct execution and organizational composer text fields begin at two visible lines, grow to an exact six-line content viewport, then scroll internally while retaining their visible top and bottom inset. Native navigation remains uninterrupted, while controlled paste follows the caret to the end of the inserted content. Provider-facing draft and continuation state remains hidden execution machinery associated with the selected exact run.

Organizational messages accept managed images plus typed project file and folder references. References are validated against the addressed teammate's membership grants when work is assigned. The normal composer does not expose provider commands, skills, model selection, safety modes, context usage, Plan or Build mode, or Stop. Teammate configuration owns provider policy, while Cancel work remains a thread-level state action.

### Slash command palette

Slash commands activate only at the start of the composer. A slash inside ordinary prose remains text. The palette supports pointer, keyboard, and screen-reader selection and keeps the active option visible while navigating. All app, provider, project, and personal entries share one flat list without source headings. Every row uses a recognizable icon, a concise name, and a muted description on the same line. The menu does not repeat slash syntax or argument hints, and its bordered surface has no drop shadow. Source and argument metadata remain internal for collision precedence, filtering, and dispatch behavior. A stale entry keeps a compact visible status. The catalog is prefetched when the working folder, provider, task, or session boundary changes and remains cached for that boundary. Opening `/` never waits on provider or filesystem I/O. Ganbaru-owned commands appear immediately if a new provider catalog is still loading, and provider entries join the open palette when ready.

Selecting a command performs the action implied by that command instead of treating every command as message text. Control actions execute directly, informational actions open an anchored panel above the composer, provider turns start through their native operation, and commands requiring input switch the composer into a named mode. None of these paths insert slash syntax into the editor. Goal shows a target icon and Goal label in the footer, changes the placeholder to request an objective, and replaces Plan with Build. Discovered custom commands with argument metadata use the same input mode. Their hidden prefix is retained for retry while the person-facing draft remains plain text. Commands reject attachments and file mentions instead of silently dropping that context. Skills remain prompt content and therefore insert their value into the editor.

Ganbaru-owned commands perform shared UI actions without pretending that a provider implements them. `/plan` and `/build` select the interaction mode. Plan appears as a dismissible mode in the composer footer, while Build is the normal mode and does not add persistent chrome. `/model` opens model controls, `/permissions` opens safety controls, `/status` opens a structured provider, session, model, account, context, and rate-limit panel above the composer, and `/changes` opens the changed-file inspector. The Status panel never becomes timeline content. These shared names take precedence and suppress a duplicate provider catalog entry, so selecting and typing the same visible command cannot produce different behavior. Selecting one of these commands removes it from the prompt and preserves focus. Typing the complete command and pressing Send performs the same action. A mode command followed by request text changes the mode and sends only the request text.

Provider commands use the most authoritative available catalog and transport:

- Codex exposes only embedded actions that Ganbaru can execute through app-server. Compact calls `thread/compact/start` without creating a user message. App-server's `contextCompaction` lifecycle becomes one durable neutral activity row in the timeline. MCP calls `mcpServerStatus/list` and renders the bounded server, authentication, and enabled state in a structured panel above the composer, without creating user or assistant messages. It works from a new draft as well as an existing task. Ganbaru reuses the task's live app-server when available, otherwise it opens a bounded provider connection in the selected working folder and omits `threadId`. Code review calls `review/start`, and Goal uses the thread goal methods after entering its composer mode. Terminal-only Codex TUI actions are not copied into the embedded UI. See the official [Codex app-server reference](https://developers.openai.com/codex/app-server/).
- Claude Code uses the command list returned by SDK `initialize`. Commands are sent through the SDK control transport exactly as Claude documents for programmatic slash commands. Compact executes immediately without a visible user message, and its `compact_boundary` system event becomes the same neutral timeline activity used by Codex. A small documented fallback catalog remains visible before the first session, and the live initialization list replaces it when available. See the official [Claude Code SDK slash command reference](https://code.claude.com/docs/en/agent-sdk/slash-commands).
- Cursor and Grok use ACP `available_commands_update` as a full replacement catalog. Ganbaru sends the selected command as a normal ACP text prompt, which is the protocol-defined execution path. It does not copy terminal-only commands from either CLI. See the official [ACP session update type](https://agentclientprotocol.github.io/typescript-sdk/types/SessionUpdate.html).
- OpenCode reads `GET /command` from the workspace-scoped server and executes a matching slash request through `POST /session/:id/command`. Templates containing `$ARGUMENTS` or positional placeholders such as `$1` enter composer input mode. Other prompts continue through the asynchronous prompt endpoint. See the official [OpenCode server API](https://dev.opencode.ai/docs/server/) and [custom command reference](https://opencode.ai/docs/commands/).

Before a live provider session exists, Ganbaru may also read documented command locations inside the authorized workspace and effective provider home. Claude uses `.claude/commands`, Cursor uses `.cursor/commands`, and OpenCode uses `.opencode/commands` or `.opencode/command`. User-level Claude and OpenCode command folders are also supported. Discovery reads only bounded Markdown metadata, skips symbolic links, limits traversal depth and entry counts, preserves nested namespaces, and never turns a discovered file into a generic filesystem capability. Live provider catalogs take precedence over fallback and file-derived entries with the same command name. Stale fallback entries remain visibly marked so the provider can accept or reject them when sent.

Grok uses the installed `grok` CLI through ACP with `grok agent stdio`. Ganbaru preserves the CLI's cached login or uses the configured `XAI_API_KEY`, identifies itself through `GROK_OAUTH2_REFERRER`, and reads the current and available model IDs from ACP session setup. Model changes use `session/set_model`. The private xAI structured-question methods are normalized into the same durable question flow as other providers. The xAI prompt-completion notification can settle a turn when the corresponding prompt RPC remains open, without leaking the abandoned request slot.

Sending writes the user message, turn, attachment references, and idempotent command receipt before dispatch. A launch failure therefore leaves recoverable durable history with Retry, Edit into a new draft, and Change provider actions. A later send reuses a ready native session, but restarts or resumes a stopped or failed session even when its runtime snapshot still contains a stale session identity. Codex resume accepts the successful `thread/resume` response for the exact stored provider thread and does not require the fresh-thread-only `thread/started` notification. Structured native errors retain their provider message in the composer instead of being stringified as an opaque object. Closing the app interrupts active provider turns. Chat reconciles those turns before loading durable room state, preserves only requests backed by a live runtime session, and keeps expired approvals or questions as non-actionable history rather than restoring their controls.

During active work, the provider capability decides whether a prompt steers the turn, becomes a durable queued follow-up, or remains an unsent draft. Stop is idempotent and has a bounded stopping state. Force stop is explicit. Approvals expose only choices offered by the provider and never choose a permissive default. Structured questions preserve partial local answers and validate required fields before submission.

## Execution permission modes

Teammate membership configuration describes four permission choices. Ask for approval is the default. Approve for me uses an eligible provider-native safety classifier, Full access uses the provider's native unrestricted mode after exact device-local trust, and Custom defers to the provider's own permission configuration. The effective policy is frozen on each authorized run and shown in execution Details.

| Permission choice | Codex | Claude | Cursor and Grok | OpenCode |
|---|---|---|---|---|
| Ask for approval | Workspace sandbox with user review | `acceptEdits` | ACP approval flow | Ask rules with workspace edits allowed |
| Approve for me | Auto-review | `auto` permission mode | Unavailable | Unavailable |
| Full access | Unrestricted sandbox | `bypassPermissions` | ACP approvals accepted automatically | Allow rules |
| Custom | Effective `config.toml` configuration | Effective `settings.json` rules and default mode | Effective `cli-config.json` or `config.toml` permissions | Effective `opencode.json` or `opencode.jsonc` permissions |

Approve for me is unavailable when a provider does not expose a native action classifier. Ganbaru does not simulate it by automatically accepting generic provider requests. Managed provider policy, explicit deny rules, and provider eligibility can still restrict a selected mode.

Full access and Custom trust are device-local and require confirmation for the exact provider instance and working folder. Custom uses the same trust boundary because every supported provider configuration can grant unrestricted access. Codex resolves its effective sandbox and approval settings. Claude starts without a permission-mode override so its settings precedence and `permissions.defaultMode` apply. Cursor and Grok leave native configuration enforcement in control and do not auto-resolve approval requests. OpenCode creates or resumes the session without replacing its configured permission rules. The active turn keeps its permission snapshot even if a later draft changes modes. Provider capability differences remain visible and disabled rather than simulated.

Chat settings provides a device-local editor for the documented user configuration and global instruction files of every configured coding-agent instance. It does not translate one provider's format into another or present a shared synthetic configuration. Codex exposes `config.toml` and `AGENTS.md` from its effective home. Claude exposes `settings.json` and `CLAUDE.md` from its config directory. Cursor exposes `cli-config.json`; its global user rules remain in Cursor settings because Cursor does not document a standalone global rules file. Grok exposes `config.toml` and `AGENTS.md` from `GROK_HOME` or its default home. OpenCode exposes its global `opencode.json` or `opencode.jsonc` and `AGENTS.md`, including an explicit `OPENCODE_CONFIG` override when configured.

The provider mapping follows the official [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Claude Code permissions reference](https://code.claude.com/docs/en/permissions), [Cursor CLI permissions reference](https://docs.cursor.com/cli/reference/permissions), [Cursor rules reference](https://docs.cursor.com/context/rules), [Grok permissions reference](https://docs.x.ai/build/features/permissions), [Grok project rules reference](https://docs.x.ai/build/features/project-rules), [OpenCode permissions reference](https://opencode.ai/docs/permissions), and [OpenCode rules reference](https://opencode.ai/docs/rules/).

The editor reads and writes only backend-resolved file identifiers for the selected provider instance. The webview cannot submit an arbitrary path. Reads and writes accept UTF-8 text up to 1 MiB, reject symbolic links, and use content revisions to prevent overwriting a file changed by another process. Saves create missing parent directories, use restrictive permissions for new files, and replace the target through a sibling temporary file. Changes affect new provider sessions; an already running provider is not silently restarted.

Each generated icon passes through Vite's asset pipeline and is bundled as a same-origin local image, so desktop WebViews do not depend on cross-document SVG fragment support or a runtime network request. Search, ignored-file visibility, external opening, path copying, and file or selection attachment remain available as icon actions. Binary, oversized, invalid UTF-8, traversal, and symlink-escape paths remain unavailable. One provider turn or in-app workspace mutation can own an execution environment at a time. A second parallel agent uses a separate worktree instead of racing the same files.

The bottom dock remains closed until the person opens it. When opened for a workspace draft, it starts with a running Terminal. The draft allocates its future thread ID before the first message, and the first send persists that same ID, so its terminal remains attached without being recreated or transferred. One tab row holds terminal sessions and any Review, Plan, or Files panels the person adds through the adjacent add menu. In both the bottom dock and right inspector, every tab has the same moderate fixed width and can be smoothly dragged left or right into one shared order. The tab strip scrolls horizontally when its fixed tabs no longer fit, while panel controls remain reachable. Middle-clicking a tab closes it with the same safeguards as its close button, including confirmation for a running terminal, and draggable tabs retain the normal pointer instead of advertising a special drag cursor. Right-clicking any tab opens a compact, shadowless rename panel with save, cancel, and reset actions. The keyboard context-menu shortcut opens the same editor. Custom names belong to that tab in its thread session, and reset restores the current automatic label. This avoids stacked tab bars and permanent tool tabs while keeping every panel available without replacing the conversation or right inspector. Terminals are thread-scoped pseudoterminals owned by Rust. Their canonical names retain the local user, device, and workspace path for terminal context metadata, while the automatic tab label shows only the path beginning at the home-relative `~` when available. Long names fade at the tab edge, and a terminal can be closed from the tab on hover. Terminal panels do not expose restart, clear, or context utility toolbars. Tabs retain bounded sequenced output. The terminal resolves theme colors and uses a cross-platform coding font stack with regular output weight instead of inheriting the application text font or relying on a CSS variable that xterm cannot resolve. Multiline paste and closing a running session retain explicit confirmation. The webview never receives a generic shell command capability.

Source control runs through bounded Rust services with fixed process arguments, deadlines, output limits, and disabled interactive credential prompts. An authorized empty working folder can clone an HTTPS or SSH repository, while an existing folder can be initialized explicitly. Initialization performed by Ganbaru or another local tool is reconciled when the stable folder identity is unchanged. Git continuity uses the filesystem identity of Git's common storage directory, not a branch or remote URL, so ordinary repository configuration remains mutable. Linked worktrees resolve through their common Git directory before identity comparison. Stage, unstage, diff, commit, fetch, fast-forward pull, push, branch, remote, and worktree reads remain typed. Review snapshots bind immutable Git endpoints and a content revision to stable file and hunk identities. Whole-scope, file, and eligible hunk stage or unstage actions revalidate that revision under a per-environment mutation lock. Revert requires explicit confirmation and never applies a patch supplied by the webview. Unstaged discard, branch deletion, force push, and worktree removal require explicit confirmation. Commit signing follows the user's Git configuration and a signing failure is reported without retrying unsigned. Hosted pull or merge requests use `gh`, `glab`, or `az` when available. Bitbucket uses bounded REST requests and stores its credential only in the operating-system keyring.

Git workspaces capture hidden refs under `refs/ganbaru-ai/chat/` using an isolated index. Capture does not move HEAD, change branch, touch the real index, alter staging, or modify working files. Restore first produces a revision-bound preview with affected files and warnings. Native provider rollback must succeed before filesystem restore when available. Confirmed restore preserves the target branch and staging state, invalidates later conversation projections durably, and queues only exact later refs for cleanup.

Browser preview tabs persist their current URL, title, viewport, loading state, and visibility in the active vault. Their child webviews remain process-local and are recreated only when the person reopens a stored tab. Switching threads hides the previous thread's visible child webview. Closing a stored tab removes it even after an application restart.

The Browser panel verifies loopback URLs found in bounded output from the current thread's terminals before offering them as local development servers. Manual loopback entry remains available. A screenshot captures only the visible child webview and becomes a managed PNG resource. Recording requires explicit confirmation, permits one active recording, captures at two frames per second for at most 15 seconds, and stores a ZIP containing bounded PNG frames and a versioned manifest. Capture failure or platform denial never disables navigation, interaction, semantic snapshots, or diagnostics. OpenCode probes its language-server and formatter endpoints and reports their current counts with provider health.

## Data ownership and retention

| Data | Location |
|---|---|
| Channels, DMs, task discussions, reply threads, participants, memberships, messages, drafts, links, and provenance | Active vault SQLite database |
| AI teammate identities, role revisions, scoped memberships, memory, work assignments, budgets, and subscriptions | Active vault SQLite database |
| Agent runs, provider threads, canonical execution events, projections, receipts, checkpoints, and cleanup | Active vault SQLite database |
| Project working-folder identity and execution-environment identity | Active vault SQLite database |
| Managed image and text attachment bytes | Active vault `assets/chat/attachments/` |
| Absolute workspace paths, executable paths, provider homes, provider-instance resolution, probe caches, diagnostics, full-access trust | Device-local application state |
| Provider tokens and passwords | Operating-system credential store behind opaque references |
| Provider processes and terminal sessions | Memory owned by the current app process |

Organizational conversation history and execution history have separate retention. Archiving a channel or task does not silently delete linked runs. Deleting a provider continuation does not erase messages, decisions, or canonical Projects records that reference its results. Archiving an AI teammate preserves its policies, memberships, messages, mentions, and assignments. Permanent teammate deletion is limited to archived identities with no durable communication or work references. Other permanent deletion requires confirmation, evaluates shared references and future collaboration visibility, removes only rows owned by the requested scope, and records deferred attachment or checkpoint cleanup before destructive external work. Attachments remain while referenced and use a grace period before file deletion. Checkpoint cleanup always names an exact hidden ref.

Future membership and access rules apply to direct reads and every derived surface. Search, mentions, backlinks, notifications, digests, reports, exports, and AI context packages cannot reveal a conversation or resource that the effective participant cannot read. Revoking access stops future reads and context assembly without rewriting legitimate history already shared with other authorized participants.

Optional protocol diagnostics are off by default, redacted, bounded, device-local, and retained for 1 to 30 days. Users can inspect captured field categories, export the same redacted representation, delete diagnostics immediately, stop all Chat processes, and rebuild projections only when runtime and durable-turn safety checks pass.

## Responsive and accessible behavior

Chat keeps the fixed explorer, conversation, and inspector columns while they fit, moves the inspector to a sheet next, then presents the explorer as a focus-contained sheet below the Chat header. A collapsed column explorer leaves its 2.75 rem restoration strip. At the 280 by 180 recovery floor, the header and one primary surface remain usable, and every essential action remains reachable. Layout changes preserve the selected room and run, drafts, reply state, undo state, timeline anchor, search, explorer expansion, inspector state, terminal state, approvals, and questions.

The inspector and bottom-dock separators support pointer and keyboard resizing with accessible values and reset actions. The explorer has no resize affordance. Pointer resizing is coalesced to animation frames, and panel transitions are disabled during the gesture so the tree and editor track the pointer without delayed interpolation. Modal surfaces enter useful focus, contain Tab navigation, and restore their trigger. Statuses use text or shape in addition to color. Live regions announce provider state, settled responses, approvals, questions, errors, and Stop without reading every streamed delta. English and Spanish catalogs use locale-aware formatting. Reduced motion removes smooth scrolling, transitions, and progress animation.

## Performance contract

Chat's route shell is resident with the other primary surfaces. After project metadata activates, the app prewarms one lightweight navigation projection containing active channels and current-run status for every non-archived project, then warms the remembered channel's newest page for the selected project. Channel navigation batches current-run shells instead of issuing one thread read per channel. A fresh `#general` with no linked session skips the timeline query entirely. Opening Chat reuses this single-flight work, and an unusually early route switch still presents a stable `#general` loading row instead of an empty rail.

The first bounded discovery pass completes before Chat publishes its initial ready state. This prevents provider-dependent controls and teammate drafts from observing an incomplete catalog. Later refresh probes remain in the background and do not block channel navigation, ordinary messaging, drafts, history, or search. Cached settings make healthy providers available immediately when possible, while full working-folder reconciliation starts only after the communication shell is usable.

Archived rooms load only when the archive opens. Historical provider sessions are not retained merely to render navigation. The selected channel reads one unified newest page, and older pages load only when scrolling requires them. Live provider changes refresh that bounded page, its channel summary, and its interaction state without rescanning the old provider-thread navigation list. Recently visited channel pages use a byte-bounded least-recently-used working set, while distant pages, expanded execution payloads, attachments, diffs, and archived history remain outside resident memory. Search stays database-backed and independent from the retained working set. Short metadata reads do not show a loading interstitial; a delayed status appears only when work lasts long enough to require feedback. Cache limits are benchmark-controlled implementation policy rather than a promise that all conversations remain in RAM.

The unrecorded `dense-chat-v1` benchmark covers 20 projects, 80 channels, 100 linked provider sessions, 2,000 turns, 4,000 messages, 4,000 activities, 1,000 plans, 500 attachments, 200 checkpoints, and 10,000 canonical events in the isolated benchmark database. Each project has `#general` plus three purpose channels, and `#general` contains two ordered provider sessions. Later fixture versions add DMs, memberships, linked tasks, attention views, and larger multi-run rooms after the current profile has recorded results.

The benchmark measures route activation, recent-room or run switching, latest-page SQLite read and projection, loaded and indexed rail search, streamed paint cadence, app process-tree idle CPU, memory, and owned process stop. The target latest-page read is normally below 100 ms, indexed search below 150 ms, normal stop below two seconds, and streaming is coalesced to paint frames. Performance results are recorded only from the installed release benchmark harness using the method in [Performance benchmark harness](performance-benchmark.md).
