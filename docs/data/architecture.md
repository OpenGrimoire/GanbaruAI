# Data architecture

The app stores two categories of data with deliberately different mechanisms. Mixing them, or storing one as the other, creates friction every time. Keeping them separate keeps each tool used for what it is good at.

## The split

**Documents.** Diary entries, project working documents, generated reports, and user attachments. These are files on disk inside the user's Ganbaru AI folder. For markdown documents, the file is the source of truth. SQLite may hold an index for fast search, tag lookups, backlinks, and modified-at queries, but the index is rebuildable from the files.

Why markdown on disk and not in SQLite as text columns:

- Users can open, edit, sync, and back up their documents with any tool they already trust (a text editor, git, rsync, Obsidian, Syncthing).
- The Ganbaru AI folder remains useful if the app stops being maintained. AGPL plus a plain-file format means the user is never trapped.
- Conflict resolution during sync uses the same file-level tools the user already understands.

**Structured data and document graphs.** Calendar events, Notes pages and blocks, kanban tasks, work environment configs, pomodoro runs, segments, pauses, playlist definitions, project metadata. These live in SQLite. The database is the source of truth. There is no authoritative markdown file to fall back to.

Why SQLite and not markdown:

- Structured data needs relational integrity (foreign keys, cascades, atomic transactions). Markdown does not enforce this.
- Aggregations that drive analytics (focus score, break adherence, idle patterns) are SQL queries, not markdown text searches.
- The data model evolves. A schema migration is a known, scoped operation. Re-parsing a thousand markdown files of varying shape is not.

The rule is one-directional: structured data and Notes pages may be exported as markdown for collaborators or AI agents that read repos, but those exports are views, not source. They can be regenerated at any time. The reverse, treating an exported markdown file as authoritative, is forbidden unless an explicit import command converts it back into canonical rows.

## Ganbaru AI folder layout

Everything portable that the app produces lives under one folder. First launch defaults to `Documents/Ganbaru AI` in production and `Documents/Ganbaru AI Dev` in development builds, with secondary actions to choose another folder or import an existing Ganbaru AI folder from another installation. Development setup warns the user to use the dev default or a copied production folder so test data does not mix with real production data. Tauri's platform app config directory stores only device-local bootstrap and runtime state, such as the active folder pointer, benchmark state, and transient doomscrolling snapshots.

Folder setup errors are blocking and remain visible until the user starts another folder action, successfully selects a usable folder, or closes the app. The UI translates backend validation failures into user-facing guidance for non-empty unrelated folders, missing or damaged `vault.json`, unsupported folder schema versions, permission problems, missing folders, and database-open failures for `ganbaru-ai.sqlite`.

Profile settings are folder-local preferences in `config.json`. `profile.displayName` is the short local name shown where a compact profile label is needed and is capped at 25 characters. `profile.fullName` stores the optional full name for future profile surfaces and is capped at 50 characters. Empty values are valid, and surfaces that require a visible self label fall back to contextual copy such as `You`.

```
Ganbaru AI/
  vault.json                         # internal Ganbaru AI folder marker, id, display name, schema version
  config.json                        # user settings, environment definitions, blocker rulesets
  ganbaru-ai.sqlite                  # SQLite source of truth for structured data, Notes, and indexes
  notes/exports/                    # derivative markdown exports for notes (planned)
  diary/morning/, diary/evening/    # dated diary entries (markdown plus indexed fields)
  projects/{project-id}/            # per-project file attachments (PDFs, references)
  reports/                          # generated project status reports (markdown, PDF)
  assets/                           # user assets (images embedded in notes, attachments)
    notes/page-icons/               # copied local Notes page icon images
    notes/page-covers/              # copied local Notes page cover images
    project-icons/                  # copied project and group icon images
  templates/                        # phase templates, methodology templates (SWOT, BMC)
  .yjs/                             # Yjs document state cache (binary)
```

Music files stay wherever the user keeps them. The Ganbaru AI folder stores playlist definitions only, with paths or URIs into the user's music library. This avoids duplicating large audio files into the app folder and respects existing collections.

Backups go to a user-specified path **outside** the Ganbaru AI folder. Backing up the folder into itself defeats the purpose if disk corruption takes the folder.

## Database files

The user database is always `ganbaru-ai.sqlite` at the active Ganbaru AI folder root. Development and production builds keep separate Tauri app config directories and separate `app-state.json` files, so each build can point at a different folder. The benchmark harness uses device-local `benchmark.sqlite` in `app_config_dir`; it is not portable user data.

Lazy initialization: the database connection is opened on first use after a Ganbaru AI folder has been selected, not at process startup. This keeps cold start time low and allows the folder to be on a slower-than-disk path, such as an encrypted volume, without delaying the setup UI.

The Tauri integration owns SQLite in Rust through focused `sqlx` commands. Higher-level ORMs were considered and rejected: they add code to maintain, do not earn enough productivity for an app this small, and obscure the actual queries that show up in performance profiles. Plain SQL with typed command wrappers keeps the call sites direct.

## External tools and the CLI bridge

The app is not the only thing that needs to read this data. AI agents (Codex or another CLI coding agent in the integrated terminal, MCP clients), backup tools, scripts, and human collaborators all interact with the same store.

The bridge is the `ganbaru-ai` CLI (Rust binary, reads the same SQLite). It exposes structured commands (`task list`, `event get`, `export kanban`) that AI agents call via Bash. This keeps three properties:

1. One source of truth. The CLI reads what the app writes. There is no duplicate authoritative store for agents.
2. Markdown exports stay derivative. The CLI can write kanban snapshots or generated reports to a git repo for collaborators who never install the app, but those files are regenerated from the database; editing them by hand is supported only via an explicit import command where the export type supports imports.
3. External readers handle dirty state. If the app crashed and a run is mid-write, the CLI applies the same recovery semantics as the app on startup (see `algorithms/pomodoro-state-machine.md`). Aggregations always operate on a consistent view.

The MCP server is for external clients only (ChatGPT, teammate agents, and other MCP-compatible clients). Internal agent flows use the CLI directly. This keeps MCP a thin, documented surface and avoids two parallel paths to the same data.

## Source-of-truth checks

When designing a new feature, ask:

- Is this content the user would expect to exist as a file they can open without the app? If yes, it is usually a document.
- Does it have relational structure (foreign keys, aggregations, cross-record queries)? If yes, it is structured data.
- Could it be regenerated from another source? If yes, it is a cache (e.g. the `.yjs/` directory, the search index part of `ganbaru-ai.sqlite`).

Notes are the named exception to the openable-file heuristic. Their editable model is a relational page and block graph, so SQLite is canonical and markdown is import, export, or bridge output. Block UI state that affects the local document graph, such as whether a toggle block or toggle heading is open or closed, is persisted with the block payload in SQLite rather than in markdown exports.

Markdown import is an explicit conversion command, not a file watcher. The importer parses supported markdown into fresh `notes_pages` and `notes_blocks` rows, records source provenance, returns diagnostics for unsafe or unsupported syntax, and leaves the imported markdown file as external input. Later edits happen against SQLite rows, and any future markdown output is regenerated from those rows.

HTML import follows the same conversion rule. The importer sanitizes markup, converts the supported subset into canonical page and block rows, records `html` source provenance, and returns diagnostics for stripped, skipped, approximated, or unsupported content. Media references are written only when the user explicitly chooses to keep supported HTTPS references; local files must go through the shared import preparation command before any importer can copy them into managed Notes assets.

Notion API import is also an explicit local conversion command. The user provides a Notion integration token for one import request, and Ganbaru AI does not store the token or route it through hosted infrastructure. The importer uses the current public Notion API version `2026-03-11`, follows paginated page, block, comment, user, and data source endpoints, respects retry and rate-limit responses, then writes canonical SQLite pages, blocks, data source rows, comments, and source provenance. Unsupported blocks and unsupported property shapes are preserved as visible diagnostics or preservation payloads rather than hidden loss. Imported Notion file objects, file upload ids, and external references stay explicit source references unless the user chooses to keep supported external file references.

Notion export folder import is a separate local conversion command for already downloaded Notion exports. It scans the selected folder for Markdown, HTML, and CSV files, skips hidden files and the Notion `index.html` sitemap, rewrites identifiable intra-export links to local Notes links, parses document files into canonical pages and blocks, and reconstructs CSV files as local data sources with row pages. Row body Markdown or HTML files next to a CSV are consumed into the matching row page rather than duplicated as standalone pages. Imported objects use `source_provider = 'notion_export'`, optional workspace provenance supplied by the user, and diagnostics for skipped files, unsupported syntax, size limits, and file policy decisions.

Markdown export is the reverse read-only projection. It walks active canonical page and block rows, optionally includes comment rows, and returns markdown plus diagnostics for approximated or unsupported content. It does not create a second source file, sync target, or persistent export table.

Notes JSON graph export is a read-only backup and diagnostics projection over the same SQLite source of truth. It exports canonical Notes tables as grouped JSON sections, includes an export schema version, the latest applied SQLx migration version, table counts, object counts, and diagnostics, and keeps JSON payload columns as nested JSON values. It may include rebuildable search, backlink, unresolved link, and graph fact indexes so diagnostics can inspect the current projections, but SQLite FTS virtual tables and shadow tables are omitted because they are rebuildable from `notes_search_index`. Managed asset rows and asset reference rows are exported as metadata; the binary files remain in the Ganbaru AI assets folder and must be backed up with the folder for full recovery.

Notes agent bridge export is a deterministic markdown projection for local AI and scripting workflows. It reads selected active pages, optional descendants, local database view rows, linked or selected project tasks, and rebuildable backlink rows from SQLite, then writes a clearly marked derivative markdown file. It is not a sync target, backup authority, or second source of truth. It stores no export state and can be recreated from the same canonical rows whenever the user needs fresh context.

Notes import and export diagnostics are UI projections over command result DTOs. They summarize preserved, approximated, skipped, unsupported, warning, info, and error outcomes with object counts and source references where the command can provide them. Source references may be local Notes page or block links, import lines, Notion source object ids, export paths, CSV rows, properties, or SQLite table rows. They are not persisted as an authority layer, and they must not make derivative markdown, HTML, CSV, JSON, Notion export folders, or agent bridge files into sync targets.

Notes block presentation data that belongs to the document, such as a callout icon and Notion-style block color, is persisted as validated block payload data in SQLite. If a later callout icon points at a local file, the asset file belongs in the Ganbaru AI assets folder while the block payload stores only the validated file object reference.

Notes child pages are represented twice because they have two roles. The page row in `notes_pages` owns the child document and its root blocks, while the paired `child_page` block row in the parent document owns the visible page link and block order. The paired page and block share an id so rename, trash, restore, and navigation can stay synchronized without a separate join table.

Notes child databases have a visible block layer and a normalized database layer. The `child_database` block owns the position in the page body and stores the visible title plus local database, data source, and view ids when Ganbaru AI creates it. `notes_databases` stores parent identity, title rich text, icon, cover, timestamps, and optional source provenance. `notes_data_sources` stores the source data and its validated property schema JSON, including the required title property and supported local schema properties. A linked database view adds another child-database block and another `notes_databases` shell, but it does not add a `notes_data_sources` row. Its `notes_database_views.data_source_id` points at the original source, while `notes_database_views.database_id` points at the linked shell so filters, sorts, visible properties, grouping, ranges, and row open mode stay independent. Database relation properties keep their Notion-shaped page property payload on the row page, while `notes_data_source_relation_links` stores one normalized link row per source row, relation property, and target row for validation, backlinks, and search. Files properties keep their Notion-shaped file object arrays on row pages, while managed local files in those arrays are tracked through `notes_asset_references` at the data source property level. Rollup properties keep only their relation id and name, target property id and name, and calculation function in the data source schema. Computed rollup page property values are generated from active relation target rows when database rows load, then stored only in `notes_data_source_rollup_cache` as a rebuildable performance cache. Formula properties keep only their expression string in the data source schema. Computed formula page property values are generated from current row property values after relation titles and rollups hydrate, use a bounded Rust parser, AST, dependency graph, and evaluator, and are never persisted into row page properties. This also gives future sync and permissions a stable rule: permissions follow the source data source's owning database, while each linked shell controls only presentation. Imported title-only child-database blocks remain valid preservation placeholders, but local database state must grow through normalized tables instead of expanding the block payload into an untyped database blob.

Notes database row pages are normal page documents parented by a data source. A row page stores `parent_type = 'data_source_id'` and `parent_data_source_id` in `notes_pages`, keeps writable page property values in `notes_pages.properties`, and owns normal body blocks in `notes_blocks`. Table cell editing rewrites only the targeted Notion-shaped page property value, records a recoverable page snapshot before mutation, updates the row title cache when the title property changes, and reloads rows through the table view's filters and sorts. Relation cell editing also rewrites the targeted relation property and rebuilds that property's normalized link rows inside the same transaction; configured two-way relations update the inverse row property and inverse link rows when the target schema still matches. Rollup values are intentionally excluded from `notes_pages.properties`; their cache is invalidated when data source schemas change, source relations change, target row properties change, or row pages are trashed, archived, restored, or permanently deleted. Formula values are also excluded from `notes_pages.properties`; they are recalculated on database view reads, can return Notion-shaped number, string, boolean, or date formula payloads, and surface runtime failures as string formula payloads prefixed with `Formula error:`. Board card moves use the same targeted property update path for locally writable group properties, then reload grouped rows through the board view's filters, sorts, group order, and hidden group state. Calendar and timeline views use the same canonical date property values to filter overlapping row ranges, create rows on a selected date, and update date spans without duplicating row storage. Row pages do not have paired `child_page` blocks, because their visible navigation surface is the database view rather than the sidebar tree. Active row pages are searchable, duplicable, trashable, restorable, and permanently deletable through the same page lifecycle commands as other Notes pages, while sidebar root reads exclude them so database rows do not leak into top-level navigation.

Notes page duplication is a graph copy, not a markdown export or a shallow page row clone. The Rust command copies the page row, visible block rows, nested child pages, icons, covers, and child-page block pairings in one transaction. Duplicates get fresh page and block ids and omit source provenance fields so imported pages do not create multiple local rows claiming the same external object identity. Database row page duplicates keep the same data source parent and property values, and they do not create child-page blocks.

Notes page templates are first-class local Notes data. `notes_page_templates` stores the template name, optional source page id, page properties, icon, cover, and timestamps. `notes_page_template_blocks` stores the normalized template block snapshot with payload JSON, plain-text cache, sort order, and parent tree. Applying a template creates new `notes_pages` and `notes_blocks` rows in one transaction, preserving SQLite as the source of truth. Markdown and rendered HTML are never authoritative template formats. Child-page template blocks create paired local child pages with default empty bodies until full subpage template snapshots are implemented.

Notes local user identity is SQLite data scoped to the active Ganbaru AI folder. `notes_local_users` stores only a generated local user id, display name, and timestamps. It intentionally excludes email addresses, avatar URLs, hosted account ids, account providers, and telemetry identifiers. Comments, comment read state, page history, user mentions, and future self-hosted sync metadata reference this local id rather than a global account.

Notes page history is recoverable SQLite data attached to the canonical page and block graph. `notes_page_history_snapshots` stores compact snapshots of page metadata, canonical block rows, and the local author id before recoverable page or block mutations. `notes_page_history_settings` stores the local retention window, where `NULL` means keep snapshots forever. Restoring a snapshot records the current page first, then replaces page details and page body blocks from the snapshot without moving the page back to an old parent. Copying from history appends fresh block rows to the current page. Markdown and rendered HTML are never authoritative history formats.

Notes page movement updates the page parent row and the paired child-page block in one transaction. Moving under another page creates or restores the paired child-page block at the end of the destination page. Moving to the workspace hides the paired child-page block because the page is now represented by the top-level sidebar tree. The command rejects self moves and descendant moves across both page-parented descendants and block-parented child pages.

Notes page archive state is document metadata stored on `notes_pages.archived`, separate from `notes_pages.in_trash`. Archived pages stay in the graph but are hidden from active page lists, active sidebar search, active page loads, and parent validation. Unarchiving clears only the archive state. Trashing a page clears archive state and stores `notes_pages.trashed_time` so deleted content is recoverable through Trash before the 7-day retention window expires. Restoring a page clears `trashed_time`. Expired Trash cleanup permanently deletes the page subtree through the normal permanent delete path.

Notes permanent page deletion is a subtree delete, not a single-row delete. The command requires the root page to already be in Trash, walks page-parented descendants, block-parented child pages, and visible child-page blocks, deletes paired child-page blocks outside the subtree, then deletes the page rows so SQLite cascades page body blocks. The command returns deleted page ids so navigation metadata can drop stale favorites and recents.

Notes sidebar navigation metadata is UI state stored in `config.json`. Expanded page state lives under `notes.sidebarExpandedPageIds`, favorites under `notes.favoritePageIds`, and recently opened pages under `notes.recentPageIds`. The older `notes.sidebarCollapsedPageIds` key is cleared when expanded state is saved. These values never change page parent rows or block order. Sidebar page reads load page metadata only: roots, expanded direct children, favorites, recents, and selected-page ancestors. They do not load page block bodies. Selected pages can still reveal their ancestor path in the sidebar without mutating the stored expanded list.

Notes managed files are SQLite-indexed Ganbaru AI folder assets. `notes_assets` records managed relative paths under `assets/notes/page-icons/`, `assets/notes/page-covers/`, and `assets/notes/files/`, plus MIME type, size, SHA-256 checksum, source type, and available or missing storage state. `notes_asset_references` records the ownership graph from assets to pages, blocks, data source properties, comments, and future import records, so payload JSON can keep Notion-shaped file references without becoming the file registry. References are removed when an owner no longer uses an asset, while asset rows remain available for deduplication and recovery until explicit cleanup is implemented. Data source file property references are rebuilt from canonical row page properties when rows or schemas change, which deduplicates repeated files inside a property and keeps retained files protected while any row still references them. Comment attachment references are rebuilt when attachment payloads change and cleared when the comment is soft-deleted.

Import file handling goes through an explicit preparation boundary before importers write canonical Notes rows. Notion export, HTML import, and Markdown import candidates must be skipped, kept as explicit HTTPS external references, or copied from a user-selected local import folder into `assets/notes/files/`. Copying requires the same size cap, MIME or extension validation, content hashing, and managed asset registration used by local attachments. Local import references are canonicalized and must remain inside the selected import folder, so export bundles cannot smuggle parent-path or symlink escapes into the vault. External references are never fetched or copied during import; they stay explicit HTTPS references when the user chooses that policy and the target block type supports the URL shape. Notion-hosted expiring `file` URLs and API `file_upload` ids are preserved as source object references until a later user action explicitly copies bytes into local managed assets.

Notes page icons are document metadata stored in the `notes_pages.icon` JSON column, not in navigation config. The editable slice supports emoji icon objects, Notion-style native icon names and colors, reusable custom emoji, external HTTPS image icons, managed local image file icons, and null removal through the page update command. Local page icon image bytes are copied under `assets/notes/page-icons/` using content-hash file names. `notes_page_icon_assets` keeps page-icon-specific picker metadata, while `notes_assets` and `notes_asset_references` record the shared asset row and page ownership reference. The page icon JSON keeps only the validated document reference and display metadata. Rendering a missing local icon falls back to the normal page icon placeholder and marks the shared asset row missing until a later successful read marks it available again.

Notes page covers are document metadata stored in the `notes_pages.cover` JSON column. The editable slice supports external HTTPS image file objects, imported Notion-hosted file objects, imported file upload references, managed local image file objects, generated local cover images, and null removal through the page update command. Local and generated page cover image bytes are copied under `assets/notes/page-covers/` using content-hash file names. `notes_page_cover_assets` keeps page-cover-specific picker metadata, while `notes_assets` and `notes_asset_references` record the shared asset row and page ownership reference. The cover JSON keeps only the validated file object reference and display metadata. Rendering a missing local cover shows the unavailable cover state and marks the shared asset row missing until a later successful read marks it available again.

Notes database row templates are local data source assets. Template metadata is stored in `notes_data_source_templates`, and template body snapshots are stored in `notes_data_source_template_blocks` as canonical block payload rows with remappable ids. Applying a template creates a fresh `notes_pages` row under the target data source, replays stored property values against the current schema by property id, inserts fresh `notes_blocks` rows, rebuilds relation links, and invalidates rollup cache. Template blocks never replace the row page graph as the source of truth.

Notes database button properties are schema-level local actions. Their configuration lives in `notes_data_sources.properties`, while row page property JSON excludes button values because the cell is derived from the schema. The command that clicks a button validates the row, reloads the current button configuration, requires confirmation when configured, and applies only typed local row-property actions. Broad, destructive, external, or cross-database automations must not be stored as untyped action blobs.

Notes external references that belong to the document, such as bookmark URLs, bookmark captions, link preview URLs, and embed URLs, are persisted as validated block payload data in SQLite. The editor may open a user-saved HTTP or HTTPS bookmark, link preview, or embed on explicit click, but it must not fetch remote preview metadata automatically because Notes must remain private and fully offline.

Notes synced blocks are persisted as validated block payload data while their contents remain normalized child rows. Original synced blocks store `synced_from: null` and can own child rows. Duplicate synced blocks store a source block id reference and stay leaf placeholders until local synced-copy fanout and unsync operations are implemented. This preserves imported Notion data without embedding authoritative children inside payload JSON.

Notes template button blocks are persisted as validated block payload data while their reusable contents remain normalized child rows. The template payload stores only the button title as rich text. Using a template copies the loaded child block subtree into the template block's parent through normal block duplication and movement, so template output is canonical `notes_blocks` data rather than an embedded JSON expansion.

Notes button blocks are persisted as validated local action payloads while inserted content remains normalized child rows. The button payload stores a rich text label, optional icon, and bounded action list. The first action schema is `insert_blocks`, with a target position and `children` as the source. The reusable blocks themselves stay under the button in `notes_blocks`; clicking the button duplicates those child rows into the target location through normal block duplication and movement. External automations, webhook calls, mail, Slack, destructive actions, and database mutations must not be stored as untyped action blobs.

Notes media and file blocks store public file object source shapes in SQLite. New local blocks can use external HTTPS URLs or managed local attachments for image, video, audio, file, and PDF blocks. Chosen local files are copied under `assets/notes/files/`, recorded in `notes_assets`, and referenced by `notes_asset_references` rows with block ownership. Block payloads store validated `ganbaru-asset:` file objects with display metadata instead of raw filesystem paths. Managed media previews read local bytes through the Tauri asset command and therefore keep attached or imported local files available without network access. External URLs, imported Notion-hosted `file` objects, and `file_upload` ids remain explicit references: the editor does not fetch, cache, or preview them automatically, and opening them requires a user action. Import candidates use the shared import preparation command so imports cannot silently fetch remote URLs, trust raw paths, or copy files outside the user-selected import root. Property files and comment attachments add their own managed asset references instead of embedding untracked paths. Future import attachments must do the same.

Notes equation expressions are persisted as validated block payload data in SQLite. Rendering can improve over time, but the canonical value is the stored KaTeX-compatible expression string rather than generated visual output.

Notes unsupported blocks are persisted as visible, validated preservation payloads in SQLite. The `unsupported` payload keeps the imported `block_type` string when available, optional source metadata, optional raw source object data, and optional import warnings. The plain text cache includes the imported type and warnings so search and future diagnostics can find preserved unsupported content even when Ganbaru AI cannot render the original block.

Notes simple tables are persisted as a block subtree in SQLite. The parent `table` block stores table width and header flags, and each `table_row` child stores its cells as rich text arrays. The rendered table is derived from those rows, so row order, duplication, trash, and future sync can use the same block graph rules as the rest of Notes.

Notes column layouts are persisted as a block subtree in SQLite. The parent `column_list` block stores layout identity, each `column` child stores optional width ratio data, and each column owns normal editable child blocks. The editor hides column container blocks from the main document flow while preserving their row order and parent identity for duplication, trash, future resizing, and future sync.

Notes tab layouts are persisted as a block subtree in SQLite. The parent `tab` block stores an empty public payload, each direct paragraph child stores a tab label and optional tab icon, and each label paragraph owns normal editable child blocks for that tab panel. The editor hides label paragraphs from the main document flow while preserving their row order and parent identity for duplication, trash, future reordering, and future sync.

Notes toggle headings are heading 1 through heading 4 blocks with validated `is_toggleable` payload state. A heading can own child rows only when `is_toggleable` is true. The local `ganbaru_open` payload field stores whether those children are visible in the editor. This keeps toggle headings compatible with Notion-shaped heading payloads while preserving local display state offline.

Notes block links are derived from existing page and block ids. They do not add a separate storage table in the first implementation because the block id already anchors the canonical row. Opening a copied block link validates the ids in the URL hash, loads the target page from SQLite, and focuses the target block if it still exists. Page-only Notes links use the same hash format without a block id and load the target page.

Notes inline annotations are canonical rich text `annotations` values inside validated block payloads and comments. The editor can split and merge selected text ranges for bold, italic, underline, strikethrough, inline code, text color, and background color without changing block identity or sibling order. Notes inline equations are canonical rich text `equation.expression` values inside the same validated payloads, and selected text can be converted into a bounded local LaTeX expression. Notes inline hyperlinks are canonical rich text `text.link` and `href` values inside validated payloads. The editor can apply, edit, and remove links over text ranges, and the validators reject unsafe URL schemes before typed use. Local Notes URLs in rich text remain backlink inputs, so editing a link refreshes the derived backlink read model.

Notes clipboard paste is parsed into canonical block updates before it crosses the Tauri command boundary. Multi-line plain text becomes sibling block rows under the same parent, and supported markdown-like line prefixes become typed block payloads. Markdown syntax in clipboard input is an import convenience only; the editable source remains SQLite block rows and validated rich text payloads. Multi-block copy, cut, paste, duplicate, move, and delete operate on selected root subtrees through Rust commands that wrap each operation in one SQLite transaction. Copy also writes plain text to the system clipboard for interoperability, but the internal Notes clipboard stores source block ids and loaded subtree ids so paste can duplicate canonical rows, rich text payloads, and supported block comment threads without making markdown authoritative.

Notes structural block moves are SQLite graph mutations. Keyboard moves, handle actions, drag reorder, drag nesting, drag outdent, and drag-to-page all plan against the loaded block tree, flush pending block saves before the structural command, then persist a new parent plus `after` or `before` anchor through Rust. The command rejects cycles, invalid parent shapes, destination pages inside the moved subtree, and anchors that do not belong to the destination parent.

Notes undo and redo state is stored in `notes_undo_state` as bounded page-local operation snapshots. This state exists only to recover local editor history after a crash or reload. It must remain derived from `notes_pages` and `notes_blocks`; applying undo or redo uses normal block update, trash or restore, and move commands so canonical content still lives in the page and block graph.

Notes mentions are canonical rich text objects inside validated block payloads and comments. The editable mention slices support page mention objects with local page ids and local Notes hrefs, date mention objects for common date and reminder inputs, local user mention objects backed by `notes_local_users`, Notion-shaped database mention objects, and explicit `ganbaru_object` mentions for backed local projects, project tasks, calendar events, active Pomodoro runs, and loaded music items. Data source rows are real Notes pages, so row mentions use page mention objects and participate in the page backlink disclosure. Reminder mentions store local `ganbaru_reminder` metadata inside the validated date mention object. Reminder mentions, user mentions, and project task mentions create local `notes_mention_notifications` rows when blocks or comments are written. Notification rows are SQLite data linked back to the source page, block, or comment, and they are delivered by the local app process without hosted infrastructure. The app stores configurable notification preferences in `config.json`; note text is omitted from notification bodies by default, and the content preview switch is opt-in local UI state. Mention display text is part of the rich text object for import compatibility, while backlinks and navigation use stable page ids where a page target exists. Diary entry and generic local file mentions stay hidden until their canonical backing models exist. Future imported users, local object backlink indexes, inline equation indexes, and range comment anchor indexes should extend the typed model rather than storing untyped JSON.

Notes backlinks are a rebuildable SQLite projection over canonical block payloads, comment rich text, child-page pairings, page aliases, and normalized database relation links. `notes_backlink_index` stores typed backlink facts for paired `child_page` references, page mention rich text payloads, local Notes URL links, comment mentions and links, active database relation facts, database mentions, and supported local object mentions. `notes_backlink_index_state` stores a source fingerprint so reads can rebuild the projection when pages, blocks, comments, data sources, databases, relation links, or aliases change. The page backlink list reads only active page-target rows from this projection and filters out trashed blocks, deleted comments, trashed or archived source pages, and inactive data source parents.

Notes graph facts are a broader rebuildable SQLite projection for future graph and impact views. `notes_link_facts` stores typed source and target facts for pages, database row pages, blocks, properties, comments, managed files, local project, task, calendar, Pomodoro, and music objects, and external URLs. It is derived from page metadata, block payloads, row properties, comment rich text and attachments, normalized relation links, managed asset references, and alias-aware local Notes link resolution. `notes_link_facts_state` stores the rebuild fingerprint. The graph projection must remain disposable: it can be cleared and rebuilt from canonical rows without losing user content.

Notes comments are canonical SQLite rows, not page payload annotations. `notes_comment_threads` stores the discussion id, target page, optional target block, open or resolved state, and resolution metadata. `notes_comments` stores individual rich text comments, the local author id, a display-name snapshot derived from `notes_local_users`, attachments metadata, timestamps, and soft-delete state. Managed local files inside comment attachments are recorded in `notes_assets` and linked back through `notes_asset_references`; text-only edits keep existing attachment references, attachment edits replace them, and soft delete clears active references without deleting the asset rows. Editing the local display name updates existing local comment display-name snapshots so the UI does not leave stale `You` labels behind. `notes_comment_thread_anchors` stores optional inline text-range anchors for block threads with offsets, selected text, and nearby prefix and suffix context. `notes_comment_thread_reads` stores per-local-user read timestamps keyed by thread and local user. A thread is unread for that identity when a non-deleted comment by another author is newer than the stored read timestamp or no read timestamp exists. Page comments use a page parent, block comments use a block parent, and visible comment reads hide block threads when the target block is trashed. Inline anchor highlights are derived from the current block text at read time, first by exact offsets and then by context-assisted selected-text search when nearby edits moved the text. Read state is local UI metadata and must stay out of derivative markdown exports. Future sync metadata should extend these tables instead of embedding comments into block payload JSON.

Notes suggestions are canonical SQLite collaboration rows, not alternate block payloads. `notes_suggestions` stores the target page and block, original selected text, proposed replacement text, range offsets, nearby prefix and suffix context, local author snapshot, creation timestamp, and accepted or rejected decision metadata. The editor resolves suggestion anchors against the current block text at read time, first by stored offsets and then by context-assisted search when nearby edits moved the selected text. Accepting a suggestion applies the proposed replacement through the normal block rich text write path, then records accepted state on the suggestion row. Rejecting a suggestion records rejected state without changing block content. Decided suggestion state is local metadata and must stay out of derivative markdown exports. Future sync metadata should extend these rows instead of embedding suggestions into block payload JSON.

Notes collaboration operations are local SQLite sync-preparation rows for comments and suggestions. `notes_collaboration_operations` records a local sequence, operation id, entity type, entity id, operation type, page id, optional block id, actor id, actor display-name snapshot, base entity version, resulting entity version, conflict policy, JSON payload, sync state, and timestamp. The canonical comment and suggestion rows keep `sync_version` counters so each operation can state exactly which entity version it observed and produced. Create operations are append-only. Comment body updates use a last-writer-wins policy until a later CRDT comment body merge exists. Comment delete, thread resolve or reopen, suggestion accept, and suggestion reject are state transitions that future replay must only apply when the local entity is still at the recorded base version. If the base version differs, replay should surface a conflict instead of silently overriding a newer local decision. Comment read state is intentionally excluded because it is per-user local UI metadata, not shared document state.

Notes workspace search is a rebuildable SQLite FTS projection over canonical Notes rows. `notes_search_index` stores the result target and derived text for page titles, row property values, active relation target titles, cached rollup values, safe formula outputs, block `plain_text`, supported rich text metadata, comments, file captions, managed file names, and file reference metadata. Property search derives text from current data source schemas so text and rich text properties, select and status labels, dates, checkbox states, relation titles, cached rollups, and formulas use the same typed semantics as database views. Rollups are indexed only from `notes_data_source_rollup_cache`, because their canonical definition remains the schema plus relations. Formula values are recomputed through the bounded Rust evaluator and successful outputs are indexed without persisting them into row pages. `notes_search_fts` stores the FTS5 terms, while `notes_search_index_state` stores a source fingerprint so reads can rebuild the projection when pages, blocks, data source schemas, comments, relation links, rollup cache rows, assets, or asset references change. `notes_search` returns the same typed page, block, or comment result contract as before, and `notes_rebuild_search_index` forces a full local rebuild for repair or diagnostics. Alias rows use the reserved `alias` search source type once the page alias model exists; until then there is no canonical alias source to index.

Generated Notes blocks store their public payload shape in SQLite, while rendered text is derived from canonical rows. Breadcrumb paths come from page and parent rows, including unavailable ancestor rows when needed for status display, and table of contents entries come from heading 1 through heading 4 blocks. This avoids stale path or heading copies when a page title, page parent, heading text, or block order changes.

If the answer is unclear, the default is structured data in SQLite. Promoting a value to a markdown file later is easy. Demoting a markdown file with subtle structure to SQLite later is painful.
